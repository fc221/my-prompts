## 是什么

几十万到几百万行的导出，不能先把全部数据和整个工作簿放进内存再保存：要分批从数据库读、边读边写进文件（流式写入），写满一张表就换下一张，整个过程放到后台任务里跑，完成后给用户下载链接。

## 适合

订单、流水、日志明细的全量导出；财务月底要的整月交易明细；超过约 5 万行、同步接口容易超时的导出。

## 不适合

几千行的普通导出直接用「代码生成 Excel」；用户要的其实是汇总结果，就导汇总，别导百万行明细让他自己透视。

## 注意

一张工作表最多 1,048,576 行（含表头）、16,384 列，超出的行不会自动换表：pandas 直接报错，xlsxwriter 返回 -1 静默丢掉，openpyxl 的只写模式照写成 Excel 打不开的文件。所以写入时自己计数，到上限前换新表。流式写入只能从上往下按顺序写，写过的行不能回头改，合计、合并单元格、超级表这类要“回头”的东西在流式模式下做不了或要提前规划。

## 要点

- 分表：按 100 万行数据一张来切（留出表头，也方便人数），表名 明细_1、明细_2……，每张都重复表头、冻结首行；第一张前面加“说明”表，写导出条件、导出时间、总行数和每张表的行号范围。
- Python 用 xlsxwriter：Workbook 传 constant_memory 为 True，按行顺序写，写完一行就落盘；这个模式下 add_table 和 merge_range 不能用。或用 openpyxl 的 Workbook(write_only=True)，只能 append 整行、只能保存一次，冻结窗格要在写数据之前设。
- pandas 的 to_excel 是按列写的，配 constant_memory 会丢数据，而且整个 DataFrame 先要在内存里；大表要么分块读出后用 xlsxwriter 逐行写，要么改导出 CSV。
- Node 用 ExcelJS 的 stream.xlsx.WorkbookWriter：每行 addRow 后调 row.commit()，一张表写完调 worksheet.commit()，最后 await workbook.commit()；useSharedStrings 默认关，开了文件更小但更占内存，百万行时保持关闭。
- 读库：按主键游标分批（WHERE id > 上一批最后的 id ORDER BY id LIMIT 5000），不用 OFFSET 深翻页；查只读库；导出期间数据还在变的，在说明表里写清数据截止时间。
- 后台任务：超过约 5 万行就转后台任务，接口立即返回任务号，前端轮询或收通知，做法见「长任务异步化」；同一用户同时只允许 1–2 个导出任务，文件放对象存储，下载链接设有效期。
- 超过几百万行或下游是程序而不是人：导出 CSV（UTF-8 带 BOM，Excel 双击打开中文不乱码），或者按月拆成多个文件打包；在 Excel 里打开百万行本身就很慢。
- CSV 和用户可编辑的文本要防公式注入：以 =、+、-、@、制表符开头的内容前面加一个单引号；xlsx 里用字符串类型写入即可（xlsxwriter 用 write_string）。

## 提示词

给{项目}的“导出{数据名，如 订单明细}”改成支持大数据量，预计最多 {最大行数，如 300 万} 行，用{库，如 xlsxwriter / ExcelJS}。
1. 先读现有导出代码和后台任务、文件存储的写法，沿用它们。
2. 超过 {同步上限，如 5 万} 行转后台任务：接口立即返回任务号，状态有排队中、导出中（带行数）、完成、失败；同一用户同时最多 {并发数} 个导出任务。
3. 读库按主键游标分批，每批 {批大小，如 5000} 行，不用 OFFSET；查询走只读库。
4. 写文件用流式模式（xlsxwriter 开 constant_memory，ExcelJS 用 WorkbookWriter 并逐行 commit），内存占用不随行数增长。
5. 每张工作表最多 1,000,000 行数据，满了新建“明细_2”“明细_3”，每张重复表头并冻结首行；最前面加“说明”表，写导出条件、数据截止时间、总行数和每张表的行号范围。
6. 金额写数值、日期写日期；用户输入的文本按字符串写。
7. 文件上传到对象存储，下载链接 {有效期，如 24 小时} 过期；超过 {CSV 阈值，如 500 万} 行时改为导出 UTF-8 带 BOM 的 CSV 并打包。
8. 测试：造 210 万行假数据，检查分成 3 张表、行数正确、内存平稳。
最后说明改了哪些文件和实测耗时、内存。
