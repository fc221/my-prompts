## 是什么

请求进入业务代码之前，按 schema 统一检查类型、必填、长度、范围、枚举和格式，不合格的直接拒绝，并一次把所有字段的问题都告诉调用方。业务代码只处理已经合法的数据。

## 适合

新接口定校验规则；老项目的校验散在 service 里、有的接口漏了；前端反馈“改掉一个错，提交后又冒出下一个”。

## 不适合

错误响应的整体结构看「错误响应格式」；“这个用户能不能改这张订单”是权限问题，看「权限模型」；库存够不够、订单能不能取消这类依赖当前数据的判断是业务规则，在领域层判断并返回业务错误码。前端表单的即时提示看「表单校验与错误提示」。

## 注意

校验只放在边界一处：控制器入参模型（DTO）上的声明式规则，和 OpenAPI 契约保持一致或直接从它生成。另一个常见漏洞是把请求体直接绑定到数据库实体，客户端多传一个 status 或 merchant_id 就改掉了不该改的字段。

## 要点

- 在入口统一校验：Spring 用 Bean Validation（@Valid），FastAPI 用 Pydantic 模型，NestJS 用 ValidationPipe 配 class-validator，其他 Node 项目可用 Zod；规则写在入参模型上，service 里不再零散判断格式。
- 每个写接口有专用入参模型，只列客户端可写的字段；id、status、合计金额、商户 id、创建人由服务端决定，不从请求体取。
- 未知字段：请求体出现模型里没有的字段时返回错误并写出字段名（如把 remark 拼成 remak），帮调用方尽早发现拼写错误；老接口要收紧时先记日志观察一个发布周期。
- 规则写全：字符串都有最大长度（备注 500、名称 64），数字有范围（数量 1–999），数组有上限（单次最多 100 个商品），枚举列出全部取值，手机号按 11 位大陆号码校验，金额用整数分且大于 0；请求体总大小在网关限制为 1MB，上传接口除外。
- 字段之间的约束也在入口校验：结束时间晚于开始时间；配送方式为 DELIVERY 时收货地址必填。
- 一次返回全部错误：按「错误响应格式」放进 errors 数组，每项含 field（用路径写，如 items[2].quantity）、code（REQUIRED、TOO_LONG、OUT_OF_RANGE、INVALID_FORMAT）和 message；JSON 解析失败返回 400，字段校验失败用哪个状态码按「状态码怎么选」统一。
- 校验前统一规范化：去掉首尾空格、全角数字转半角；超长、越界一律报错，不悄悄截断后照存。
- 金额、价格以服务端计算为准，客户端传来的合计只用来比对，不一致返回错误。

## 提示词

检查{服务}的入参校验并改正。先列出所有接口的入参模型，找出：没有校验的接口、写在 service 里的格式判断、请求体直接绑定到实体的地方、缺少长度或范围限制的字段、只返回第一个错误的接口。
按以下规则改：
1. 用 {校验库，如 Bean Validation、Pydantic、Zod} 在入参模型上声明规则，入口统一触发，删掉 service 里的格式判断。
2. 每个写接口用专用入参模型，只含客户端可写字段；服务端决定的字段（id、status、合计金额、商户 id）不从请求体取。
3. 请求体出现未知字段时返回错误并写出字段名。
4. 每个字符串有最大长度、数字有范围、数组有上限、枚举列出取值，字段之间的约束一并校验。
5. 校验失败一次返回全部错误，errors 数组每项含 field 路径、code、message；JSON 解析失败返回 400。
6. 金额以服务端计算为准。
最后说明改了哪些文件，并给 {示例接口，如 POST /orders} 写测试：一次提交三个错误字段能全部返回、多传 status 字段被拒绝、超长备注被拒绝。
