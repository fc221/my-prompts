## 是什么

客户端给每个写操作生成一个唯一键，放在 Idempotency-Key 请求头里；服务端记住这个键和第一次的结果，同一个键再来时直接返回第一次的响应，不再执行一遍。让 POST 这类本身不幂等的操作也能安全重试。

## 适合

下单、支付、退款、发券、充值这类重复执行会多扣钱、多发货的操作；移动网络下的超时重试；网关或 SDK 的自动重试。

## 不适合

GET、PUT、DELETE 按语义本来就幂等，见「方法与幂等」；接收 Webhook 时的重复事件用事件 id 去重，见「Webhook 设计」；前端防连点只改善体验，后端仍要靠幂等键或唯一约束兜底。

## 注意

键按“一次业务操作”生成，不按“一次 HTTP 请求”：用户点一次“提交订单”生成一个键，网络重试沿用同一个，改了内容再提交才换新键。服务端存储时要把键和调用方身份绑在一起，两个商户碰巧用了相同的键不能串到对方的结果。

## 要点

- 请求头 Idempotency-Key，值用 UUID v4，长度上限 255；标准草案把值写成带双引号的字符串，解析时两种写法都接受。
- 存储的唯一键是（调用方 id, 幂等键），同时存请求指纹（方法 + 路径 + 请求体的 SHA-256）、状态（processing 或 completed）、响应状态码和响应体。
- 保留 24 小时后删除；文档写明保留时长，超过这个时间的重试按新请求处理。
- 同键、同请求体、已完成：原样返回第一次的状态码和响应体，加响应头 Idempotent-Replayed: true。
- 同键不同请求体返回 422，错误码 IDEMPOTENCY_KEY_REUSED；同键的第一个请求还在处理中返回 409，客户端稍后用同一个键重试。
- 要求幂等键的接口没带时返回 400，错误码 IDEMPOTENCY_KEY_REQUIRED；文档列出哪些接口必须带。
- 只保存确定的结果（2xx 和参数类 4xx）；5xx、429 和超时不记为完成，删掉 processing 记录，允许客户端用同一个键重试。
- 实现：先插入 processing 记录，靠唯一约束抢占；业务写入和把记录改为 completed 放在同一个数据库事务里，避免“扣了款却没记下结果”。

## 提示词

给{服务}的写接口加上幂等键（已有就检查并改正）。先列出所有有副作用的写接口，标出重复执行会造成损失的（{关键接口，如 POST /orders、POST /refunds}），再读现有的防重逻辑：靠什么去重、存在哪里、保留多久、并发时会不会两个请求都执行。
按以下规则改：
1. 关键接口要求带 Idempotency-Key 头，缺失返回 400。
2. 以（调用方 id, 幂等键）为唯一键，存请求指纹、状态和响应，保留 {保留时长}。
3. 同键同请求返回第一次的响应并加 Idempotent-Replayed: true；同键不同请求体返回 422；第一次还在处理返回 409。
4. 5xx、429 和超时不记为完成，允许同键重试。
5. 抢占记录靠唯一约束，业务写入和标记完成放在同一个事务里。
6. 前端和 SDK 按一次用户操作生成键，重试时沿用。
最后说明改了哪些文件，并写测试覆盖：同一请求并发发两次只扣一次款、改了金额沿用旧键返回 422、第一次返回 500 后用同一个键重试能成功。
