## 是什么

两类记录：访问日志记下每一次 API 调用（谁、什么时候、调了哪个接口、结果和耗时），用来排查问题和统计用量；审计日志记下关键操作（谁对哪个资源做了什么、改前改后），用来追责和合规，只增不改。

## 适合

开放平台要回答“这笔订单是哪个商户用哪把 Key 改的”；退款、改价、导出会员数据、改权限这类敏感操作；按调用方统计用量和计费；等保和内控检查。

## 不适合

日志格式和采集管道看「结构化日志」；指标和链路追踪看「指标与链路追踪」；给用户看的操作记录（订单时间线）属于业务数据，单独建表设计。

## 注意

日志最容易泄露敏感信息：Authorization 头、令牌、密码、身份证号、银行卡号整段写进日志，而日志系统的权限往往比数据库松。默认不记请求体和响应体，确实需要时按字段白名单记录并脱敏。

## 要点

- 每个请求有 request id：入口读取 X-Request-Id，没有就生成，透传给下游，响应头原样返回，错误响应体的 traceId 也用它；接入方报障时提供这个 id。
- 访问日志一请求一行 JSON：时间、request_id、调用方（app_id、Key 前缀、user_id、tenant_id）、方法、路由模板（写 /orders/:id，不写带具体 id 的原始路径，便于聚合）、状态码、错误码、耗时毫秒、请求和响应字节数、客户端 IP、User-Agent。
- 脱敏：Authorization、Cookie、密码、令牌不记录；手机号记成 138****5678，身份证号和银行卡号只留末 4 位；脱敏在日志组件里统一做，不靠每个接口自己处理。
- 审计日志单独存储：操作人、调用方、时间、动作（refund.create、member.export、role.update）、资源类型和 id、结果、来源 IP、变化字段的改前改后值；只允许追加，应用账号没有更新和删除权限。
- 必须审计的操作：资金类（退款、改价、调账）、批量导出、权限和角色变更、凭证的创建和吊销、安全配置变更（改 IP 白名单、改回调地址）。
- 留存：访问日志至少 180 天（网络日志法定留存不少于六个月），审计日志按内控要求更久（如 3 年）；到期按策略归档或删除。
- 用量和告警：按调用方汇总调用量、错误率、P95 耗时，异常时告警（某把 Key 的 401 突增、单个调用方的导出量突增）；接入方后台能查自己近 30 天的调用记录。

## 提示词

给{服务}加上调用日志与审计（已有就检查并改正）。先读日志中间件、日志配置和现有的操作记录表，盘点：有没有 request id 并贯穿到下游、访问日志记了哪些字段、哪些地方把请求体或令牌写进了日志、敏感操作有没有审计、日志存多久。
按以下规则改：
1. 入口统一处理 X-Request-Id，透传下游，在响应头和错误响应的 traceId 里返回。
2. 访问日志一请求一行 JSON，含调用方、路由模板、状态码、错误码、耗时；默认不记请求体和响应体。
3. 日志组件统一脱敏：不记 Authorization、Cookie、密码和令牌，手机号、身份证号、银行卡号按规则打码。
4. {敏感操作列表，如 退款、改价、导出会员}写审计日志：操作人、调用方、动作、资源、结果、IP、变化字段的改前改后值；审计表只允许追加。
5. 访问日志保留至少 180 天，审计日志保留 {审计保留期}。
最后说明改了哪些文件，并演示：用一个 request id 查到从网关到下游的完整调用；做一次退款后能查到对应的审计记录；在日志里全文搜索不到令牌。
