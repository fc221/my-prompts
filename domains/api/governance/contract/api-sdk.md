## 是什么

从契约生成各语言的客户端代码，外面再包一层手写的薄封装，处理认证、重试、分页、错误类型这些每个调用方都要写的东西。调用方装一个包就能用，不用自己拼 HTTP 请求、算签名。

## 适合

开放平台给商户和服务商提供 Java、Python、Node.js、Go 等语言的包；内部多个服务调用同一组 API；前端调自家后端，想要完整的类型。

## 不适合

调用方只有一两家、接口很少时，好文档加 curl 示例就够，见「接口文档与示例」；前端项目里的请求层怎么组织看「请求层封装」「接口类型生成」。

## 注意

生成的代码不手改，改了下次生成就被覆盖。需要定制的逻辑放进手写封装层或生成器模板，生成代码放单独目录，文件头标明“自动生成，勿改”。

## 要点

- 用 openapi-generator 或各语言的专用生成器，配置和模板进仓库；契约一变，CI 自动重新生成并开 PR；生成目录（generated/）和手写封装分开。
- 认证内置：初始化时传 Key 或客户端凭证，SDK 负责加头、在过期前刷新令牌，并提供现成的 Webhook 验签方法。
- 重试内置：只对 429、502、503、504 和网络错误重试，最多 3 次，指数退避加抖动，有 Retry-After 就按它等；POST 自动生成 Idempotency-Key，重试时沿用。
- 默认超时写明（连接 5 秒、读取 30 秒），可以按单次调用覆盖。
- 分页给迭代器：调用方写一个循环就能遍历全部订单，翻页由 SDK 完成。
- 错误类型化：按状态码和错误码抛不同异常（AuthenticationError、RateLimitError、ValidationError），异常里带 HTTP 状态、错误码、字段错误和 traceId。
- 版本号按 semver，独立于 API 版本；破坏性改动升主版本并附迁移说明；请求带 User-Agent（如 store-sdk-python/2.3.1），服务端据此统计各版本用量，决定何时停止支持旧版。
- 发布到 npm、PyPI、Maven Central 这类官方仓库，README 首屏就是安装命令和一段能跑的示例；CI 对每种语言用 mock 服务跑一遍冒烟测试。

## 提示词

为{服务}生成并封装 {语言列表} SDK（已有就检查并改正）。先读 OpenAPI 契约和现有的 SDK 或调用方代码，盘点：是否从契约生成、生成代码有没有被手改、认证和重试是不是每个调用方各写一遍、错误怎么暴露、版本怎么发布。
按以下规则改：
1. 用生成器从契约生成到 generated/ 目录，配置和模板进仓库，契约变更时 CI 自动重新生成并开 PR。
2. 手写封装层负责：加认证头和刷新令牌、Webhook 验签方法、对 429、502、503、504 和网络错误最多重试 3 次并遵守 Retry-After、POST 自动带 Idempotency-Key、默认超时、分页迭代器。
3. 按错误码抛类型化异常，带状态码、错误码、字段错误和 traceId。
4. 版本号用 semver 且独立于 API 版本，User-Agent 带 SDK 名和版本。
5. README 首屏给安装命令和可运行示例；CI 对 mock 服务跑冒烟测试。
最后说明改了哪些文件，并用 SDK 演示：列出全部{资源名}（自动翻页），以及模拟一次 429 后自动重试成功。
