## 是什么

几类最容易出错的字段的统一格式：时间用 RFC 3339 带时区，金额用最小货币单位的整数或字符串小数，ID 一律用字符串。定一次，全库照用。

## 适合

新服务定字段规范；排查“前端拿到的订单 ID 末尾几位变了”“金额加起来差一分”“海外门店的时间差了 8 小时”这类问题。

## 不适合

前端怎么显示日期和数字看「日期时间」「数字与表格排版」；数据库列类型看「表设计约定」。

## 注意

JavaScript 的 Number 只能精确表示 2^53（约 9007 万亿）以内的整数，19 位的雪花 ID 传给前端会被舍入成另一个数，查出来是别的记录或查不到。金额用浮点数传和算，会出现 0.1 加 0.2 不等于 0.3，对账对不上。

## 要点

- 时刻用 RFC 3339 字符串并带时区：2026-03-08T14:30:00+08:00，或 UTC 的 2026-03-08T06:30:00Z；服务端按 UTC 存，返回时统一用 Z 还是带偏移，全库一种。
- 纯日期（生日、营业日、报销所属月份）写 2026-03-08、2026-03，不带时间和时区，避免换时区后差一天；和地点有关的时间（门店营业时间）另给 timeZone 字段，如 Asia/Shanghai。
- 时长用整数加单位后缀（durationSeconds、timeoutMs）或 ISO 8601 时长（PT30M），全库一种。
- 金额二选一：最小货币单位的整数（amount 为 12990 表示 129.90 元，字段说明或命名里写明单位是分），或固定小数位的字符串（"129.90"）；计算全程用整数或十进制类型。
- 多币种时金额旁边带 currency（ISO 4217 代码，如 CNY、USD），小数位按币种处理，日元没有小数。
- ID 在 JSON 里一律是字符串，数据库里是 bigint 也一样；可以带资源前缀方便排查，如 ord_8F3k2Lx、mbr_93Kd1。
- 比例和费率用字符串小数（rate 为 "0.0125"）或整数基点（rateBp 为 125），文档写清。
- 入参按同一套格式校验：不带时区的时刻、带小数的分、数字类型的 ID 都返回 400，错误里写期望的格式。

## 提示词

统一{服务名}的时间、金额和 ID 格式。先读实体、DTO、JSON 序列化的全局配置和前端的格式化工具。
1. 列出所有时间、金额、ID 字段，以及它们现在的类型和格式。
2. 时间：时刻返回 RFC 3339 带时区的字符串，服务端按 UTC 存；纯日期用 YYYY-MM-DD；和地点有关的时间另给 timeZone。
3. 金额：{分为单位的整数 / 两位小数的字符串}，计算全程用整数或十进制类型；多币种时带 currency。
4. ID：JSON 里全部输出为字符串，入参也按字符串接收。
5. 优先在序列化层全局配置，个别字段再单独处理。
6. 入参格式不对返回 400，错误里写期望格式。
7. 测试：19 位 ID 往返不变，0.1 加 0.2 这类金额计算准确，+08:00 和 Z 两种写法解析到同一时刻。
最后列出改动文件，以及对前端和对接方有影响的字段清单。
