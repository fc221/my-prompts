## 是什么

不兼容的变更怎么发布：版本号放在路径（/api/v1/orders）还是请求头，几个版本怎么共存、各维护多久。

## 适合

API 给 App、小程序、第三方商户调用，客户端升级慢、新旧要长期并存；第一次要做不兼容改动。

## 不适合

能兼容的改动（加字段、加可选参数）直接发布、不升版本，判断方法看「向后兼容规则」；只给自家前端用、能和前端同时发布的 API，通常一个版本就够；旧版本怎么通知和关闭看「弃用与下线」。

## 注意

版本号只在不兼容变更时升，升的是整套 API 的主版本，不是单个路径各自编号。每多一个版本就多一套要测试和维护的代码，同时在线的主版本最多两个。

## 要点

- 默认把主版本放路径：/api/v1/orders；只写主版本号，不写 v1.2。
- 对外开放平台可以改用请求头版本（如 Api-Version: 2026-03-01 这样的日期版本），需要网关支持；和路径版本二选一。
- 路径版本每个请求都显式带上；请求头版本缺省时固定到一个具体版本（如调用方首次接入时的版本），不随新版本发布自动切换。
- 新主版本发布后，旧版本至少维护 6–12 个月，对外开放的 API 取更长，期限写进文档。
- 代码组织：各版本共用领域层和数据库，只在控制器和 DTO 层分开；旧版本的请求转换成内部模型后走同一套逻辑。
- 每个版本有自己的 OpenAPI 文档和变更日志，列出和上一版的全部不兼容差异及迁移示例。
- 监控按版本和调用方统计调用量，作为下线旧版本的依据。
- App 和小程序在请求头里带客户端版本（如 App-Version: 5.12.0），方便按客户端版本定位问题和提示强制升级。

## 提示词

给{服务名}引入版本管理，准备发布不兼容的变更：{变更内容}。先读路由前缀、网关配置、现有接口文档和调用方清单。
1. 版本放在路径：/api/v1、/api/v2，只用主版本号；现有接口全部归到 v1，路径和行为不变。
2. v2 只在控制器和 DTO 层分开，复用同一套服务层和数据库；v1 的请求转成内部模型后走同一逻辑。
3. 生成 v1、v2 两份 OpenAPI 文档，再写一份变更日志：每个不兼容差异的旧写法、新写法和迁移示例。
4. 按版本和调用方打点调用量。
5. v1 维护 {维护时长}，到期前按「弃用与下线」发通知、加响应头。
6. 测试：v1 原有用例全部通过，v2 新用例覆盖每个变更点。
最后列出改动文件和调用方需要做的事。
