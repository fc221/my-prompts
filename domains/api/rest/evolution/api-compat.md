## 是什么

一份“哪些改动不会弄坏老客户端”的清单。判断标准只有一条：老客户端不改代码，照样能正确工作。兼容的改动直接发布，不兼容的走新版本。

## 适合

每次改 API 前自查；代码评审时判断要不要升版本；给 App、小程序这类升级慢的客户端提供 API。

## 不适合

已经确定不兼容、要发新版本看「版本管理」；契约变更在流水线里怎么自动卡住看「契约优先」。

## 注意

破坏常常藏在“只是顺手改一下”的地方：枚举加一个值、可选字段改成必填、校验长度收紧、默认排序变了。这些都会让老客户端出错，要么按不兼容处理，要么事先在对接文档里写好客户端的容错义务。

## 要点

- 兼容：新增 API、新增响应字段、新增可选请求参数（有默认值且默认行为不变）、放宽校验（长度上限变大）、新增错误码（客户端能按状态码兜底时）。
- 不兼容：删除或改名字段；改字段类型或格式（数字 ID 改字符串、金额单位从元改分）；非空字段变成可能为 null；可选变必填；收紧校验；改状态码、默认值、默认排序或分页行为；改已有错误码的含义。
- 枚举加值：对接文档事先写明“客户端必须处理未知值”时才算兼容，否则按不兼容处理。
- 对接文档写清客户端的容错约定：忽略不认识的响应字段，未知枚举值走兜底显示，不依赖字段顺序和错误文案。
- 字段改名分两步：先新旧字段同时返回、旧字段标 deprecated，旧字段调用量归零后再删。
- 行为变了也算变更：同一请求返回的数据范围、副作用（多发一条短信）、耗时量级（从 50ms 变成 5s）变了，都写进变更日志并通知调用方。
- 流水线里对比新旧 OpenAPI 文档，自动标出不兼容变更；出现时要求升版本或在提交里显式确认。

## 提示词

评估这次对{服务名}的改动是否向后兼容。先读改动的 diff、受影响 API 的现有文档和已知调用方（{调用方}）。
1. 列出每个 API 的变化：请求字段、响应字段、类型和格式、必填性、校验规则、枚举值、默认值、状态码、错误码、副作用。
2. 每项标“兼容 / 不兼容 / 有条件兼容”，并说明哪个老客户端会怎么出错。
3. 不兼容的给出兼容改法：加新字段而不是改旧字段，新旧字段并存一段时间，新行为用新参数开启；确实做不到的，转到新版本。
4. 枚举加值时，检查对接文档是否写明客户端要处理未知值。
5. 在流水线加 OpenAPI 新旧对比，发现不兼容变更时让检查失败，除非提交里显式标记。
最后输出结论（能否直接发布）、需要通知的调用方和一份变更日志草稿。
