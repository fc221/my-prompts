## 是什么

按场景挑 HTTP 状态码的对照表：成功、客户端错误、服务端错误各用哪几个，分别带什么响应头。状态码给网关、监控和客户端做第一层判断，更细的原因放进错误体的 code。

## 适合

新服务定状态码规范；老接口要从“全部 200、body 里放 code”迁移出来；前端要按状态码统一处理登录过期、无权限和重试。

## 不适合

错误体的字段看「错误响应格式」；限流的配额和响应头细节看「限流与配额」；业务错误码怎么编号、怎么在代码里抛看「错误处理与错误码」。

## 注意

只用一小组常用状态码，每个码的含义全项目一致。拿不准时问一句“客户端改了请求能不能成功”：能就是 4xx，不能就是 5xx。细分原因靠错误体里的 code，不靠冷门状态码。

## 要点

- 成功：查询和更新返回 200 带资源；创建返回 201，Location 指向新资源（/orders/ord_8F3k2），响应体是完整资源；受理后台处理返回 202，Location 指向任务地址 /jobs/:id；删除或无内容返回 204，响应体为空。
- 400：请求解析不了或参数格式、类型不对，如 JSON 语法错、page=abc、时间不带时区；422（Unprocessable Content）：格式正确但违反业务规则，如报销金额超出额度、开始时间晚于结束时间、修改只读字段。
- 401：没带凭证或凭证无效、过期，带 WWW-Authenticate 头，客户端刷新令牌或重新登录；403：身份已知但没有权限，如店员审批报销；404：资源不存在，访问别的门店的会员这类不该暴露存在性的场景也返回 404。
- 409：和资源当前状态冲突，如取消已发货的订单、同一手机号重复注册；412：带了 If-Match 但 ETag 已变，见「缓存与并发控制」；428：要求带 If-Match 却没带。
- 429：触发限流，带 Retry-After 秒数；另外三个常用的：405 方法不支持（带 Allow），413 请求体过大，415 Content-Type 不支持。
- 5xx：500 是未预期异常，只返回通用提示和 traceId；502 / 504 是上游出错或超时；503 是主动降级或维护，带 Retry-After。
- 客户端按状态码分流：401 刷新令牌后重放一次；403 提示无权限，不重试；409 / 412 提示刷新后再改；429 / 503 按 Retry-After 重试；其余 4xx 直接展示错误。

## 提示词

统一{服务名}的 HTTP 状态码。先读全局异常处理、各控制器的返回值和前端请求层的错误处理。
1. 列出现状：参数解析失败、业务校验失败、未登录、无权限、资源不存在、状态冲突、并发修改、限流、未预期异常，各返回什么。
2. 按这套对照改：创建 201 带 Location，异步受理 202 带任务地址，删除 204；解析失败 400，业务规则不通过 422；未认证 401 带 WWW-Authenticate，无权限 403，访问不属于自己的资源 404；状态冲突 409，If-Match 不匹配 412；限流 429 带 Retry-After；未预期异常 500 只返回 traceId。
3. 映射集中写在全局异常处理里，业务代码只抛带错误码的异常。
4. 同步改前端请求层：401 刷新令牌后重放一次，409 / 412 提示刷新，429 / 503 按 Retry-After 重试。
5. 每个状态码至少一条集成测试。
最后列出改动文件，以及对现有调用方有破坏的变更。
