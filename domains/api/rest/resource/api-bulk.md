## 是什么

一次请求处理多条记录，如批量导入会员、批量关闭工单、批量调价。关键是先定整批原子还是逐条处理，以及部分成功时怎样返回每一条的结果。

## 适合

后台勾选多行后统一操作；一次提交几十到几百条数据；客户端把多次小请求合成一次，减少往返。

## 不适合

上万条或处理超过十几秒的看「长任务异步化」；表格文件导入看「文件上传与下载」；单条 API 循环调用也不慢时，直接用单条 API。

## 注意

部分成功最容易做错：整体返回 200 但其中几条失败，前端只看状态码就会提示“全部成功”。每条结果都要带自己的状态和错误，并能用下标或客户端给的 clientId 对应回请求里的那一条。

## 要点

- 路径：批量动作用 POST /集合/batch-动作，如 POST /tickets/batch-close；批量创建用 POST /members/batch；请求体是 items 数组。
- 单批上限写进文档并校验，常用 100 或 500 条，超出返回 422，错误码如 BATCH_TOO_LARGE，提示分批提交。
- 先定语义并写进文档：原子（全部成功或全部回滚）适合调价、库存调整；逐条处理适合导入和批量关闭工单。
- 原子批量任一条失败返回 422，errors 数组列出失败条目的 index 和原因，数据保持不变。
- 逐条批量返回 200（或 207 Multi-Status，全项目统一一种），results 数组和请求顺序一一对应，每项含 index 或 clientId、status、成功时的 id、失败时的 error，另给 succeeded 和 failed 计数。
- 批量请求支持 Idempotency-Key，重试时返回第一次的结果；批量删除遇到不存在的 ID 记为成功还是单条 404，全项目统一一种。
- 每一条都走单条 API 的权限和校验逻辑，逐条检查数据范围（只能关闭本门店的工单）。
- 超过约 1000 条或预计处理超过 10 秒时，改成提交任务并返回 202，见「长任务异步化」。

## 提示词

给{资源名}加批量{操作}接口。先读现有的单条接口、校验和权限逻辑，批量版本复用它们。
1. 路径：POST {集合路径}/batch-{动作}，请求体是 items 数组，单批最多 {单批上限} 条，超出返回 422。
2. 语义：{原子 / 逐条}。原子时任一条失败整批回滚，返回 422，errors 里写失败条目的 index 和原因；逐条时返回 200，results 和请求一一对应，每项含 index、status、成功的 id 或失败的 error，外加 succeeded、failed 计数。
3. 每条都走单条接口的权限和校验，按数据范围逐条检查。
4. 支持 Idempotency-Key，重放时返回第一次的结果。
5. 前端按 results 逐行提示，部分失败时保留失败行，改完可以只重试这些行。
6. 测试：全部成功、部分失败、超过上限、重复提交、混入越权条目。
最后列出改动文件，并说明单批上限的取值理由。
