## 是什么

把现有接口（路由代码、OpenAPI 文件或接口清单）交给 AI 逐项审查，按严重程度列出问题、影响和改法，并区分能直接改的和需要发新版本的。

## 适合

接口上线或对外开放前；接手老项目；联调时前端反复反馈格式不统一。

## 不适合

从零设计用「从需求设计一组接口」；只判断一次改动兼不兼容看「向后兼容规则」。

## 要点

- 材料越接近运行时越可靠：从服务导出的 OpenAPI、路由注册代码、真实的请求和响应样例，都比需求文档准。
- 写清哪些接口已有外部调用方，AI 才分得出“直接改”和“要发新版本”。
- 问题多时先修严重和高两级，其余记进待办。

## 提示词

请审查{服务名}的接口设计。材料：{OpenAPI 文件 / 路由目录 / 接口清单}。已有外部调用方的接口：{已对外的接口}。
通读全部接口后逐类检查：
1. 路径：复数名词、kebab-case、嵌套不超过两层，除状态迁移 POST /资源/:id/动作外没有动词。
2. 方法：GET 无副作用；PUT、DELETE 重复调用结果不变；会被重试的 POST 有 Idempotency-Key。
3. 状态码：201 带 Location、202 带任务地址、204 无响应体；400 与 422、401 / 403 / 404、409 与 412 区分正确。
4. 错误：统一 RFC 9457（type、title、status、detail、instance 加 code、errors），500 不暴露内部信息。
5. 列表：流水类用游标分页；过滤和排序字段有白名单。
6. 字段：时间 RFC 3339 带时区，金额为分的整数或字符串小数，ID 为字符串，同一资源各处字段一致。
7. 演进：多人编辑的资源用 ETag 加 If-Match；弃用接口带 Deprecation 和 Sunset。
8. 权限：每个接口有数据范围检查，越权返回 403 还是 404 规则一致。
按严重程度输出（严重：丢数据、越权、资损；高：调用方必然出错；中：不一致、难用；低：命名和文档），每条写接口、问题、影响、改法、是否兼容（不兼容的标“需新版本”）。最后给按优先级排好的修改计划，先不改代码。
