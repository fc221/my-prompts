## 是什么

把一段业务需求交给 AI，让它先列资源清单和接口清单，写清每个 API 的方法、路径、请求和响应字段、错误码和权限，你确认后再写代码。

## 适合

新模块开工前前后端一起对接口；需求文档只有页面描述，没有接口定义。

## 不适合

挑已有接口的问题用「审查接口设计」；清单定好后要出机器可读的契约用「生成 OpenAPI 契约」。

## 要点

- 需求原样贴进引号里，原型的文字说明、页面字段的转写都可以一起贴。
- 写清调用方和角色，权限和数据范围那一列才写得准。
- 先看【假设】和【待确认】，改完再让它写代码或出 OpenAPI。
- 在已有项目里用时，AI 会先读现有路由和响应包装；新项目就补一句路径前缀和字段大小写风格。

## 提示词

我要为{模块}设计一组 REST 接口，需求如下：
“{需求}”
调用方：{Web 后台 / 小程序 / App / 第三方}；角色：{角色列表}。

先读项目里已有的路由、响应包装、错误结构和权限定义，新接口沿用它们。先不要写代码，按下面几段回复：
【资源清单】列出资源（复数 kebab-case），每个写主要字段、和其他资源的关系、有哪些状态以及怎么流转。
【接口清单】每个 API 一项：方法、路径（路径参数写 :id，嵌套不超过两层）、用途、所需权限和数据范围（如“店长只能看本门店”）、是否幂等（会被重试的 POST 是否要 Idempotency-Key）。状态迁移用 POST /资源/:id/动作。
【字段】每个 API 的请求字段（名称、类型、必填、校验规则、示例值）和响应字段；列表写清分页方式、可过滤和可排序的字段。时间用 RFC 3339 带时区，金额用分为单位的整数，ID 用字符串。
【错误】每个 API 可能返回的状态码和业务错误码，各用一句话写触发条件。
【假设】你替我做的默认选择，逐条列出。
【待确认】最多 5 个会影响接口的问题，每个附推荐答案；我不回答就按推荐做。

我确认后，再按清单生成控制器、DTO、校验和接口测试。
