## 是什么

浏览器和服务端之间保持一条双向长连接，双方随时都能发消息。适合高频、双向的实时场景，代价是心跳、重连、补发和多实例分发都要自己做。

## 适合

门店后厨的接单屏、工单的在线客服会话、多人协同编辑、骑手实时位置；客户端也要频繁上行消息的场景。

## 不适合

只需服务端单向推送（订单状态变化、AI 流式回答）用「SSE 流式输出」，走普通 HTTP，代理和鉴权都更简单；系统之间的事件通知用「Webhook 设计」；每分钟一次的低频更新直接轮询。前端怎么接入看「实时数据接入」。

## 注意

连接静默失效是常态：手机切后台、换网络、负载均衡空闲超时，都不会触发任何报错。没有心跳就发现不了断线；没有序号和补发，断线期间的消息就丢了。

## 要点

- 心跳：客户端每 25 秒发一条应用层 ping 消息（浏览器的 WebSocket API 发不了协议层的 ping 帧），服务端回 pong；任一方 60 秒没收到对方任何消息就断开重连。负载均衡和网关的空闲超时要大于 60 秒。
- 重连用指数退避加抖动：等待时间在 0 到 min(30 秒, 1 秒乘以 2 的重连次数次方) 之间随机取，连上并稳定 1 分钟后计数清零；收到 4001（令牌失效）先刷新令牌再连，收到 4003（无权限）停止重连。
- 消息统一信封：type（order.created、ping、ack）、id、seq、ts、data；seq 按频道单调递增，客户端按 seq 去重和排序。
- 补发：重连后客户端带上每个频道最后收到的 seq，服务端从缓冲区补发之后的消息；缓冲区每个频道保留最近 5 分钟或 1000 条，超出范围时回一条 resync，客户端改为重新拉一次全量。
- 鉴权：浏览器建连带不了自定义头，先调 HTTP 接口换一张 60 秒内有效、只能用一次的票据，放在连接 URL 的 ticket 参数里；握手时校验 Origin 白名单；令牌过期时服务端以 4001 关闭连接。
- 订阅按频道：subscribe、unsubscribe 消息带频道名（如 store:<门店id>:orders），服务端校验用户对该频道的权限，单连接订阅数设上限（如 50）。
- 限制和关闭码：单条消息不超过 64KB，超出用 1009 关闭；正常关闭用 1000；服务端发版前给每个连接发 1012（服务重启），客户端按退避重连，不会在同一秒全部涌回。
- 多实例：业务代码只往频道发布消息，各实例通过 Redis Pub/Sub 或消息队列收到后推给本机上的连接，不关心用户连在哪台机器。

## 提示词

给{服务}的 WebSocket 推送加上心跳、重连和补发（已有就检查并改正）。先读服务端的连接处理、鉴权、消息发送代码和前端的连接封装，盘点：消息格式、有没有心跳、断线怎么重连、断线期间的消息会不会丢、怎么鉴权、多实例时怎么找到用户所在的连接。
按以下规则改：
1. 消息统一为 type、id、seq、ts、data 信封，seq 按频道递增。
2. 客户端每 25 秒发 ping，任一方 60 秒收不到消息就断开。
3. 重连用指数退避加全抖动，上限 30 秒；4001 先刷新令牌再连，4003 停止重连。
4. 重连后按频道带上最后的 seq，服务端补发最近 {缓冲时长} 内的消息，超出时发 resync，客户端重新拉全量。
5. 建连用一次性短期票据，握手校验 Origin，订阅时校验频道权限。
6. 发版前给所有连接发 1012；多实例之间用 {消息总线} 分发。
最后说明改了哪些文件，并演示：断网 20 秒后恢复，期间产生的 {业务事件，如新订单} 能补齐且不重复。
