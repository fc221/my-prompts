## 是什么

自己系统里发生事件时（订单已支付、工单已关闭），主动向接入方登记的 URL 发一个 POST。两头都要设计：发送方负责签名、重试和投递记录，接收方负责验签、快速应答和去重。

## 适合

开放平台给商户推订单、退款、物流状态；接入第三方支付、短信、物流的回调；内部系统之间不方便直连消息队列时的事件通知。

## 不适合

推给浏览器或 App 前台用「SSE 流式输出」「WebSocket 实时推送」；内部服务之间优先用消息队列，见「事件驱动与消息队列」；需要同步拿到结果的直接调 API。

## 注意

Webhook 是至少一次投递：网络超时后发送方会重发，接收方一定会收到重复事件，也可能乱序。接收方用事件 id 去重，按资源的当前状态处理，不按到达顺序推断状态。

## 要点

- 请求体：id（事件唯一 id，evt_ 开头）、type（资源.过去式，如 order.paid、refund.succeeded）、created_at、data（资源快照，或只放资源 id）；同一事件重发时 id 不变。
- 签名：请求头带 Webhook-Id、Webhook-Timestamp（Unix 秒）和 Webhook-Signature；签名内容是“事件 id.时间戳.原始请求体”，用接入方密钥做 HMAC-SHA256 后 Base64 编码，头里写成 v1,签名值。
- 接收方验签：用原始请求体字节计算（不能先解析 JSON 再序列化），用常量时间比较；时间戳与当前时间相差超过 5 分钟直接拒绝，防止重放。
- 应答：接收方 5 秒内返回 2xx，只做验签、落库、入队，业务处理放到后台任务；发送方只把 2xx 当成功，不跟随 3xx，超时和其他状态码都进入重试。
- 重试计划：1 分钟、5 分钟、30 分钟、2 小时、6 小时、12 小时、24 小时，首次之外共 7 次重试，每次加 10% 随机抖动；全部失败后标为失败、通知接入方并提供手动重发；连续失败超过 3 天的端点自动停用。
- 去重：接收方给事件 id 建唯一索引，插入冲突就直接回 2xx；处理前按 data 里的资源 id 查一次最新状态，或比较 updated_at，忽略比当前状态旧的事件。
- 密钥轮换：接入方后台可生成新密钥，过渡期（如 24 小时）内同时用新旧密钥各签一份，Webhook-Signature 里用空格分隔多个签名，接收方任一通过即可。
- 安全和可查：只投递到 HTTPS 地址，登记时拒绝内网和回环地址（防 SSRF）；每次投递记录请求、响应状态和耗时，接入方后台能查最近 30 天的投递记录。

## 提示词

检查{服务}的 Webhook {发送 / 接收}实现并改正。先读事件产生、投递（或回调接收）的代码和相关表结构，盘点：请求体格式、签名算法和签名内容、时间戳校验、超时和重试、去重方式、失败后怎么处理。
发送方按以下规则改：
1. 请求体固定为 id、type、created_at、data，重发时 id 不变。
2. 签名头 Webhook-Id、Webhook-Timestamp、Webhook-Signature，对“id.时间戳.原始请求体”做 HMAC-SHA256。
3. 只把 2xx 当成功，单次超时 {超时秒数} 秒；按 1 分钟到 24 小时退避重试 7 次并加抖动；全部失败后标为失败，支持手动重发，投递记录可查。
接收方按以下规则改：
1. 用原始请求体验签，常量时间比较，时间戳偏差超过 5 分钟拒绝。
2. 5 秒内返回 2xx，业务处理放后台任务。
3. 事件 id 建唯一索引去重；处理前按资源 id 查最新状态，忽略过期事件。
最后说明改了哪些文件，并写测试覆盖：签名错误、时间戳过期、同一事件投递两次、先收到新状态再收到旧状态。
