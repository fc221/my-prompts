## 是什么

给某一种前端（App、小程序、管理后台）单独配一层后端，把多个领域服务的数据聚合、裁剪成页面需要的形状，顺带处理登录态和协议转换。业务规则仍然留在领域服务里。

## 适合

一个页面要调五六个服务才拼得出来（会员首页要会员、积分、优惠券、推荐）；App 和后台对同一资源要的字段差别大；想把令牌留在服务端，浏览器只拿会话 Cookie。

## 不适合

只有一个前端、接口本来就贴合页面时不加这一层；端多、字段差异大且变化频繁，考虑「GraphQL Schema 设计」；只转发不聚合的用网关就够。

## 注意

BFF 最容易长成第二个业务层：在里面算价格、判断能不能退款。规则一旦写在这里，App 和小程序的两个 BFF 很快会算出不一样的结果。BFF 只做取数、组合、裁剪和格式转换。

## 要点

- 按端划分：每种客户端一个 BFF（app-bff、mini-bff、admin-bff），由该端的前端团队维护；BFF 之间不互相调用。
- 只调领域服务的接口，不直连业务数据库；判断、计算、状态流转都在领域服务里。
- 一个页面对应一个聚合接口（GET /app/home、GET /app/orders/:id/detail），返回结构对应页面区块，页面用不到的字段删掉。
- 互不依赖的下游调用并发发出；整个请求有总超时预算（如 800ms），每个下游单独设超时，且不超过剩余预算。
- 下游分必需和可降级：订单主体失败就整体返回错误；推荐、广告、积分失败时返回空值，并在响应的 degraded 数组里写出降级的区块名（如 recommend），前端据此隐藏该区块。
- 登录态在 BFF 收口：浏览器用 HttpOnly、Secure、SameSite=Lax 的会话 Cookie，BFF 凭会话取访问令牌再调下游，令牌不下发到浏览器。前端侧的做法见「登录态与令牌」。
- 透传 X-Request-Id 和用户身份给下游，每次下游调用记录耗时，便于定位慢在哪个服务。

## 提示词

给{产品}的{客户端}加一层 BFF（已有就整理）。先读前端各页面的请求，统计每个页面调了哪些服务、调几次、串行还是并发；再读现有 BFF 或网关代码，找出写在里面的业务判断和计算。
按以下规则改：
1. 每个页面一个聚合接口，路径用 /{客户端前缀}/页面名，返回结构对应页面区块，删掉页面用不到的字段。
2. BFF 只调领域服务的接口，不连业务数据库；找到的业务判断（价格计算、权限、状态能否流转）列出来，迁回对应的领域服务。
3. 互不依赖的下游并发调用，总超时 {总超时}，每个下游单独设超时且不超过剩余预算。
4. 每个下游标为必需或可降级：必需的失败就整体报错；可降级的返回空值，并在 degraded 数组里写明区块名。
5. 登录态改为 HttpOnly 会话 Cookie，令牌只在 BFF 和下游之间流转；透传 X-Request-Id。
最后列出改了哪些文件、每个页面改前改后的请求次数和耗时，并演示一个可降级的下游超时后页面仍能正常返回。
