## 是什么

同一组业务能力可以用 REST、GraphQL 或 gRPC 暴露，差别在谁来调、要不要 HTTP 缓存、字段由谁决定、需不需要流式。先按调用方定协议，再谈细节；常见组合是对外 REST、对内 gRPC，多端聚合时再加 GraphQL 或 BFF。

## 适合

新项目定接口形式；拆服务时决定服务之间怎么调；App、小程序、管理后台对同一份数据要的字段差别很大，在犹豫要不要上 GraphQL。

## 不适合

已经定了 REST、要设计具体接口，看「资源命名与路径」「错误响应格式」；只是要服务端主动推消息，看「WebSocket 实时推送」「SSE 流式输出」；系统之间的事件通知看「Webhook 设计」。

## 注意

按调用方和团队能力选，不按新旧选。GraphQL 把查询成本交给了客户端，没有深度和复杂度限制就上线，等于开放了一个任意查询的入口；gRPC 浏览器不能直接调，要经过 gRPC-Web 或网关转码。

## 要点

- 对外开放给第三方、合作伙伴、开放平台：REST + OpenAPI。调用方工具最全，GET 能用上 HTTP 缓存和 CDN，签名、限流、网关都现成。
- 服务之间的内部调用、延迟敏感、需要流式或多语言强类型：gRPC + Protobuf，见「gRPC 与 Protobuf」。
- 多个前端读同一张关系图（门店、商品、库存、会员价），各端要的字段和嵌套差别大、迭代快：GraphQL，见「GraphQL Schema 设计」；只有两三个端、差异主要在聚合和裁剪时，用「前端专用后端（BFF）」更省事。
- 以写操作为主的流程型业务（下单、支付、退款、审批）用 REST 或 gRPC，GraphQL 的 mutation 在这里没有优势。
- 文件上传下载、需要浏览器或 CDN 缓存的资源留在 REST，见「文件上传与下载」。
- 推送单独选：单向推送和 AI 流式输出用 SSE，双向高频用 WebSocket，跨系统通知用 Webhook。
- 一个系统的主协议最多两种，每种都有 schema 文件进仓库，错误码在协议之间一一对应。
- 选定后写进架构文档：每种协议用在哪一层、谁维护 schema、兼容性检查在哪一步做。

## 提示词

为{产品}选接口形式。先读现有代码和部署方式，列出全部调用方：{调用方列表，如 App、小程序、门店管理后台、第三方 ERP、内部订单服务}，以及每个调用方的调用量、是否由浏览器直接调用、是否需要实时推送。
1. 逐个调用方判断用 REST、GraphQL 还是 gRPC：对外开放和需要 HTTP 缓存的用 REST + OpenAPI；内部服务之间、延迟敏感或要流式的用 gRPC；多端读同一张关系图且字段差异大的才考虑 GraphQL，差异主要在聚合时改用 BFF。推送场景单独在 SSE、WebSocket、Webhook 里选。
2. 全系统主协议不超过两种。画出分层：哪一层对外、哪一层对内、网关在哪里做协议转换。
3. 已有接口里和选型不一致的，列出迁移清单和先后顺序，分批改，不一次全换。
4. 输出选型说明 docs/api-style.md：结论、每种协议的使用范围、schema 文件位置、兼容性检查方式，以及出现哪些情况时需要重新评估。
