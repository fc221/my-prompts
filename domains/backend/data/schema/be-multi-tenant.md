## 是什么

同一套服务给多家企业用时，保证 A 公司读不到、改不到 B 公司的数据。常见三种做法：共享表加 tenant_id 列、每个租户一个 schema、每个租户一个库；隔离越强，成本和运维负担越重。

## 适合

SaaS 化的工单、报销审批、进销存系统；集团下多家门店或子公司共用一套系统；一套后台服务多个品牌商户。

## 不适合

只有一家客户的内部系统；同一租户内按部门、按本人可见属于权限问题，看「权限模型」；按用户量拆库扩容量看「读写分离与分库分表」。

## 注意

共享表方案的最大风险是某一条查询漏了 tenant_id 条件：不报错，只是悄悄串数据。过滤条件要由框架统一注入、数据库兜底，而不是靠每个人记得写。

## 要点

- 选型：租户多、单个租户数据量不大，用共享表加 tenant_id；有合规要求或单独计费的大客户给独立 schema 或独立库。可以混用，租户到库的映射放在一张路由表里，代码只认这张表。
- 租户来源：tenant_id 只取自认证后的上下文（令牌里的租户，或校验过的子域名）；请求参数和请求体里的 tenant_id 一律忽略，或要求与上下文一致，不一致返回 403。
- 表结构：每张业务表带 tenant_id BIGINT NOT NULL，联合索引和唯一索引都以 tenant_id 开头，如唯一索引 (tenant_id, expense_no)；跨租户共用的字典表单独标明，不加 tenant_id。
- 统一注入：ORM 层用全局过滤自动追加租户条件并在插入时自动填充（Hibernate @TenantId、MyBatis-Plus 租户插件、EF Core 全局查询过滤器、Django 自定义 Manager）；绕过过滤器的原生 SQL 显式带 tenant_id，并在评审里单独标出。
- 数据库兜底：PostgreSQL 对业务表 ENABLE 并 FORCE ROW LEVEL SECURITY，策略条件用 tenant_id = current_setting('app.tenant_id')::bigint，应用账号不是表的 owner、没有 BYPASSRLS；MySQL 没有行级安全，靠框架注入加 SQL 审计扫描兜底。
- 连接池：租户上下文用 SET LOCAL 在事务内设置，事务结束自动失效；会话级 SET 会让归还到池里的连接带着上一个租户的设置。缓存键、对象存储路径、消息体、日志都带 tenant_id。
- 后台任务和定时任务没有登录上下文，进入任务时显式设置租户、结束时清理；跨租户的运营统计走单独的只读账号和单独的代码路径。
- 测试：准备两个租户的数据，用租户 A 的身份对每个列表、详情、修改、导出接口传入租户 B 的 id，全部返回 404 或 403，这组用例进 CI。

## 提示词

检查并加固{项目}的多租户隔离，当前方案是{共享表加 tenant_id / 每租户一个 schema / 每租户一个库}，数据库是{MySQL / PostgreSQL}。
1. 盘点：逐表确认 tenant_id 是否 NOT NULL、索引是否以它开头；找出原生 SQL、批量更新、导出、后台任务和缓存键里没带租户条件的地方；确认 tenant_id 从哪里取。
2. 按规则改：tenant_id 只从认证上下文取，请求里传入的值不一致返回 403；ORM 层加全局租户过滤和插入自动填充；原生 SQL 显式带租户条件；后台任务进入时设置租户上下文；缓存键和文件路径带租户。PostgreSQL 再开启并 FORCE 行级安全，用 SET LOCAL 传租户，应用账号不是表 owner。
3. 加一组跨租户越权测试：用租户 A 的令牌访问租户 B 的每类资源，断言 404 或 403。
4. 汇报：缺少隔离的位置清单、改动文件、新增迁移和测试，以及测试结果。
