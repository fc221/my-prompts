## 是什么

把读多写少、查询或计算昂贵的数据放进 Redis 或进程内存，减轻数据库压力。要定清楚三件事：缓存什么、什么时候过期、数据改了缓存怎么跟着变。

## 适合

商品详情、门店信息、会员等级规则、配置和字典、首页聚合数据；同一份数据每秒被读几百次、一天只改几次。

## 不适合

余额、库存这类每次读都要准的数据，读主库或靠数据库条件更新；只读一次的数据加缓存只增加复杂度；击穿和雪崩的防护看「缓存穿透、击穿与雪崩」；HTTP 层的缓存头看「缓存与并发控制」。

## 注意

更新时“先删缓存再写库”和“写库后直接更新缓存”，并发下都可能把旧值写回缓存并一直留着。默认用“先提交数据库、再删除缓存”，并且所有缓存键都有过期时间兜底。

## 要点

- 默认模式 Cache-Aside：读时先查缓存，未命中查库后写回；写时先提交数据库事务，提交成功后删除缓存键（而不是改写它）；删除失败进入重试队列，或订阅 MySQL binlog / PostgreSQL 逻辑复制统一删除。
- 键名：服务:实体:标识:版本，全小写冒号分隔，如 mall:product:detail:10086:v2；值的结构变了就升版本号，不用批量清旧键；多租户系统键里带租户 ID。
- TTL：每个键都有过期时间，基础值按变化频率定（字典 1 天、商品详情 30 分钟、首页聚合 1–5 分钟），再加 0–20% 的随机抖动，避免一批键同时过期。
- 值：只放用得到的字段，序列化用 JSON 或 Protobuf 并带结构版本；单个值尽量在 10KB 以内，超过 1MB 的大 key 拆开；集合数据用 Hash、ZSet 按需读写，不整块读写大列表。
- 两级缓存：极热且能容忍几十秒不一致的数据（会员等级规则、全局配置）再加一层进程内缓存（Caffeine、ristretto、lru-cache），TTL 30–60 秒、设容量上限，变更时通过 Redis Pub/Sub 广播失效。
- 范围：结果随用户权限不同的，按用户或角色分键；筛选条件组合无穷的列表页不缓存整页，只缓存单个实体。
- 降级：缓存操作超时 50–100ms；Redis 超时或不可用时直接查库（配合查库并发上限），缓存故障不导致请求失败。
- 监控命中率、未命中时的查库耗时、内存和大 key；命中率低于 80% 时回头检查键设计和 TTL。

## 提示词

为{项目}的{数据，如商品详情、门店信息}加缓存或检查现有缓存，缓存用{Redis / Redis 加进程内缓存}，数据库是{MySQL / PostgreSQL}。
1. 盘点：列出这类数据的读写入口、估算的每秒读写次数、现有缓存键和 TTL；标出没有过期时间的、写库前删缓存或直接改写缓存的、键名不统一的、Redis 故障会让请求失败的地方。
2. 按规则改：读走 Cache-Aside；写在事务提交后删除缓存，删除失败进入重试；键名统一为 服务:实体:标识:版本；TTL 按变化频率定基础值再加 0–20% 随机抖动；缓存操作超时 100ms 以内，Redis 不可用时降级查库。
3. 补测试：更新后再读拿到新值；停掉 Redis 后接口仍然正常返回。
4. 汇报：缓存了哪些数据、键名和 TTL 一览、改动文件、压测或线上日志里的命中率对比。
