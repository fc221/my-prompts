## 是什么

缓存挡不住、流量直接压到数据库的三种情况。穿透：查的数据根本不存在，每次都打到库；击穿：一个热点键过期的瞬间，上千个请求同时去库里重建；雪崩：大量键同时过期，或 Redis 整体不可用。

## 适合

大促和直播间的爆款商品详情；被人用随机 ID 刷的查询接口；Redis 重启、扩容、主从切换的预案。

## 不适合

缓存怎么设计、怎么保持一致看「缓存策略」；整体流量超过系统容量，靠「限流与配额」和扩容。

## 注意

防击穿的互斥锁要有过期时间和兜底：拿到锁的请求查库失败或卡住时，其他请求不能一直等。防穿透缓存空值时 TTL 要短，否则数据真创建出来以后，很长时间里还是查不到。

## 要点

- 穿透：查不到的数据缓存一个空值标记，TTL 30–60 秒；有固定格式的 ID 先校验格式（订单号长度、前缀不对直接 404）；ID 空间大、容易被枚举的，在缓存前加布隆过滤器，新数据写入时同步加入。
- 击穿：热点键重建时只放一个请求查库。单进程内合并并发加载（Go 的 golang.org/x/sync/singleflight，Caffeine 的 get 加载函数会让同键并发请求等同一次加载）；多实例用 Redis SET NX 互斥锁（5 秒过期），没拿到锁的等 50ms 重读缓存，最多 3 次，之后返回旧值或降级结果。
- 逻辑过期：极热的键（大促主会场商品）不设物理过期，值里带 expire_at，过期后先返回旧值，由单个后台任务刷新；活动开始前预热，活动期间定时刷新。
- 雪崩：所有 TTL 加基础值 0–20% 的随机抖动；导入、预热这类批量写入的键错开过期时间；Redis 用主从加哨兵或集群部署，能自动故障转移。
- 兜底：数据库前加并发上限（如每实例最多 50 个并发查库，超出直接返回降级数据或 503）；Redis 连续超时时按「超时、重试与熔断」打开熔断，降级到进程内缓存或默认值。
- 热 key 和大 key：定期用 redis-cli --hotkeys（需要 LFU 淘汰策略）和 --bigkeys 扫描；单个键读 QPS 上万时加进程内缓存，或复制成带 #1 到 #8 后缀的多份分散到不同节点。
- 演练：在预发布环境清空缓存、停掉一个 Redis 节点，观察数据库 QPS、连接数和接口错误率，确认不会被打垮。

## 提示词

为{项目}的{热点接口，如商品详情、活动页}补齐缓存失效防护，缓存用 Redis，峰值约{峰值 QPS}。
1. 盘点：列出这个接口用到的缓存键、TTL 和未命中时的查库路径；检查是否缓存空值、重建有没有互斥、TTL 有没有抖动、Redis 故障时怎么表现、查库有没有并发上限。
2. 按规则改：查不到的数据缓存空值 60 秒，入参先校验格式；热点键重建用进程内合并加 Redis 互斥锁（5 秒过期，没拿到锁等待重读最多 3 次，失败返回旧值）；{极热数据，如活动商品}改为逻辑过期加后台刷新，并在活动前预热；所有 TTL 加 0–20% 抖动；查库加每实例并发上限，Redis 连续超时打开熔断走降级。
3. 写压测脚本：同一个不存在的 ID 连续请求 1000 次；热点键过期瞬间 500 并发；分别记录数据库实际查询次数。
4. 汇报：改动文件、压测前后数据库查询次数对比、各种降级情况下接口返回什么。
