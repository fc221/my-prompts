## 是什么

同一个词在不同业务里含义不同：“商品”在商品中心是 SPU、SKU 资料，在订单里是下单那一刻的快照，在库存里是仓位和数量。限界上下文就是划一条边界，边界内术语和模型统一，边界之间通过明确的契约交互。它决定模块和服务从哪里切。

## 适合

业务线多、多个团队协作的系统，比如电商的商品、交易、库存、会员、营销；准备做「模块化单体」或「微服务拆分」之前先划边界；同一张表被三四个模块各自加字段、谁都不敢动的时候。

## 不适合

单一业务、一个小团队维护的系统，按功能分目录就行，不必画上下文映射；边界还看不清的早期产品，先按业务名词分目录，跑一段时间再收敛。

## 注意

边界按业务能力和业务语言划，不按技术层（“数据服务”“通用服务”）划，也不按表划。检验办法：这一块能不能由一个团队独立修改、独立发布；如果每次改它都要连着改另一块，边界就切错了。

## 要点

- 每个上下文有自己的模型和表：订单上下文保存下单时的商品名、单价快照，查订单时不去 join 商品中心的表；跨上下文只传 ID 和契约里的字段。
- 上下文之间的交互方式三选一并写下来：同步 API 调用、发布事件、共享只读的公开数据集。数据库表只由所属的上下文读写。
- 接外部或遗留系统时加防腐层：在本上下文的 adapters 里把对方的字段和状态码翻译成自己的模型，对方改字段只改这一处。
- 每个上下文维护一份术语表：“订单状态”在交易里是待支付、已支付、已完成，在履约里是待拣货、已出库、已签收，两套状态各用各的枚举。
- 目录示例：src/catalog/、src/trading/、src/inventory/、src/membership/，各自有 api/ 目录放对外契约，其他上下文只引用 api/ 里的类型；src/shared-kernel/ 只放 Money、ID 这类极少变化的类型。
- 一个上下文只由一个团队负责；一个团队可以负责多个上下文。
- 过度设计的信号：三五个人的项目划出十几个上下文、每个上下文只有一两张表、为了“解耦”把必须强一致的数据（订单和订单行）拆到两边。

## 提示词

帮我给{产品，如 社区团购平台}划分限界上下文。先读代码和表结构，列出主要的业务名词，以及同一个词在不同模块里含义不同的地方（如“商品”“订单状态”“会员”）。然后：
1. 给出上下文清单，每个写清职责、拥有的数据表、核心术语和建议的负责团队（团队情况：{团队情况，如 3 个小组共 12 人}）。
2. 用文字画出上下文映射：谁调用谁、用同步 API 还是事件、哪里需要防腐层。
3. 列出现在跨边界直接读写别人表的地方，按风险排序，给出替代做法（调接口、订阅事件、存快照字段）。
4. 标出可以放进共享内核的少数稳定类型。
这一步只输出分析和建议，不改代码；需要业务方确认的边界单独列出。
