## 是什么

领域建模的三块积木：实体有唯一标识、状态会变（订单、工单）；值对象没有标识、按值比较、不可变（金额、地址、积分数）；聚合是一组必须一起保持一致的对象，外部只能通过聚合根修改它（订单连同订单行）。

## 适合

有明确不变式的业务：订单总额等于各行之和、库存不能为负、积分余额不能透支、报销单审批后金额不能改；状态流转多、规则写在 service 里已经看不清的模块。

## 不适合

字段多、规则少的资料维护（门店信息、商品属性），对象只是数据载体，用「三层架构」加普通的数据类就够；报表和统计直接写查询，不经过聚合。

## 注意

聚合要小：一个事务只改一个聚合，聚合之间只用 ID 引用，跨聚合的一致性交给「领域事件」做最终一致。把会员、订单、积分塞进一个大聚合，并发一高就全是锁冲突。

## 要点

- 状态修改走聚合根的业务方法：order.cancel(reason)、expense.approve(approver)；方法里先校验当前状态和不变式，不满足就抛带错误码的领域错误。外部拿不到 setStatus 这类 setter。
- 值对象不可变、构造时校验：Money（整数分加币种，币种不同相加直接报错）、Points（不能为负）、PhoneNumber；两个值对象字段相同就相等。
- 实体按 ID 判断相等；ID 在创建对象时生成（雪花 ID 或 UUIDv7），不依赖数据库自增才拿到 ID。
- 划聚合边界只问一个问题：哪些数据必须在同一个事务里同时正确。订单和订单行是一个聚合；订单和会员是两个，订单里只存 memberId。
- 下单同时要扣积分时，订单聚合提交后发 OrderPlaced，积分聚合在自己的事务里扣减，失败走补偿或重试。
- 仓储只为聚合根提供，见「仓储模式」；订单行这类聚合内部对象没有自己的仓储。
- 目录示例：src/order/domain/（order 聚合根、order_line、order_status、money、order_errors）；领域对象不带 ORM 注解时，映射写在 src/order/persistence/。
- 过度设计的信号：每个字段都包成值对象、只有 get/set 的“聚合”、为了建模而加的工厂和领域服务。规则少的模块退回普通 service。

## 提示词

为{聚合名，如 报销单}按实体、值对象和聚合建模。先从现有代码和需求里整理出它的不变式（如{不变式示例，如 审批通过后金额不能再改、明细金额之和等于总额}）和状态流转。然后：
1. 确定聚合边界，说明哪些对象在聚合内、哪些只存 ID 引用。
2. 聚合根提供业务方法（{业务动作，如 提交、审批通过、驳回、撤回}），方法里校验当前状态和不变式，违反时抛带错误码的领域错误；去掉外部对状态字段的直接赋值。
3. 金额、数量这类概念做成不可变值对象，构造时校验。
4. 一个事务只改这一个聚合，需要联动别的聚合时发领域事件。
5. 每个业务方法写单测，覆盖合法流转、非法流转和边界值（金额为 0、明细为空）。
持久化映射保持现有表结构。最后用文字列出状态流转（从哪个状态、什么动作、到哪个状态）和改动文件。
