## 是什么

写操作（命令）和读操作（查询）用不同的模型：写走领域模型和业务校验，保证规则正确；读直接查为页面准备好的读模型（专用 SQL、冗余宽表、搜索索引），不经过聚合。可以同库不同模型，也可以写库、读库完全分开。

## 适合

读写形态差异大：下单要校验库存和优惠，查询却要按会员、门店、时间、状态多维筛选和统计；后台列表要 join 五六张表，写模型已经被查询需求拖得四不像；读量比写量高一两个数量级。

## 不适合

读写字段基本一致的普通增删改查，用一套模型加几个专门的查询方法就够；只是数据库扛不住，先加索引和缓存，再考虑主从复制，见「读写分离与分库分表」，那是数据库层面的分流，和模型拆分是两回事。

## 注意

读模型单独存放后就是最终一致，用户刚提交就去列表里查，可能还看不到。处理办法三选一：提交后直接展示命令返回的结果；界面上标“处理中”；“我刚下的单”这类查询走写库。

## 要点

- 从最轻的一级做起：同一个数据库，命令走 service 和聚合，查询走单独的查询类，直接写 SQL 返回 DTO。多数项目停在这一级就够。
- 第二级：为重查询建冗余读表或物化视图（如 order_list_view 冗余会员名、门店名），由领域事件或定时任务更新。
- 第三级：读模型放进搜索引擎或分析库（Elasticsearch、ClickHouse），通过事件或 CDC 同步；监控同步延迟，超过阈值（如 30 秒）告警。
- 命令只返回 ID 和必要的结果（订单号、状态）；查询只读，不改任何状态。
- 读模型可以随时丢掉重建：保留从主库或事件全量重建的脚本，读表结构变了就重建，省掉在线迁移。
- 目录示例：src/order/commands/（place_order、cancel_order）、src/order/queries/（order_list_query、order_stats_query）、src/order/projections/（更新读表的事件处理器）。
- 过度设计的信号：没有性能和复杂查询问题就上事件溯源和独立读库；简单的详情查询也绕道读模型；同步链路出问题时，没人知道读表落后了多久。

## 提示词

{模块}的查询越来越复杂（{查询需求，如 后台订单列表按门店、会员、状态、时间筛选并统计金额}），想用 CQRS 把读写模型分开。先读现有代码，说明写操作和这些查询共用了哪些对象、慢在哪里（附执行计划或耗时）。然后从最轻的方案做起：
1. 命令保持走 service 和领域模型，只返回 ID 和结果。
2. 新建 queries/ 目录，每个查询一个类，直接写 SQL 返回专用 DTO，带分页和必要的索引。
3. 只有单条 SQL 加索引仍达不到{性能目标，如 P95 300ms}时，才建冗余读表，由事件或定时任务更新，同时给出重建脚本和延迟监控。
4. 说明哪些页面会受最终一致影响，以及怎么处理。
最后列出改动文件、新增的索引和改动前后的耗时对比。
