## 是什么

把系统拆成多个独立部署的服务，每个服务负责一块业务能力、拥有自己的数据库，服务之间通过网络 API 或消息通信。换来独立发布和独立扩容，代价是分布式事务、跨服务排查和运维成本。

## 适合

多个团队（通常 30 人以上）在同一个系统上互相等发布；各部分负载差异很大，需要单独扩容（大促时下单和库存要扩 10 倍，后台报表不用）；已经有容器平台、CI/CD、集中日志和链路追踪。

## 不适合

团队不到 10 人、业务边界还在变、部署和监控能力还不成熟时，先做「模块化单体」，等边界稳定、确实需要独立扩容或发布再拆；只是想“代码分开放”，模块化单体就能做到。

## 注意

按「限界上下文」拆，不按技术层（用户服务、通用服务、数据服务）拆，也不按表拆。拆完后如果一个常见需求要同时改三个服务、一起发布，说明边界切错了。

## 要点

- 每个服务独占数据库，至少独占 schema；其他服务只能通过它的 API 或事件拿数据。共享库表的“微服务”其实是分布式单体。
- 同步调用都设超时、重试和熔断，见「超时、重试与熔断」；调用链深度控制在 3 层以内，页面需要的聚合数据交给网关或「前端专用后端（BFF）」组装。
- 跨服务的写操作走最终一致：「Saga 长事务」编排步骤和补偿，「发件箱模式」保证事件不丢。
- 每个服务有独立的 CI 流水线、部署和版本；服务间契约（OpenAPI、Protobuf）集中放在 contracts/，合并前做兼容性检查。
- 可观测性是前提：全链路透传 W3C traceparent，每个服务输出结构化日志和请求量、错误率、耗时三类指标，见「指标与链路追踪」。
- 拆分顺序：先拆边界最清楚、变化最频繁或负载最特殊的一块（如库存、消息推送），用绞杀者方式在单体前面按路由逐步把流量切过去，一次只拆一个。
- 目录示例：services/order-service/、services/inventory-service/、services/member-service/，各自含 src/、migrations/、Dockerfile 和部署配置；contracts/ 放接口定义；platform/ 放网关和公共部署模板。
- 过度设计的信号：服务数是团队数的两三倍以上、一个请求要串五六个服务、几个服务总是一起发布、本地起不来整套环境就没法开发。

## 提示词

评估并规划{系统}的微服务拆分。现状：团队{团队规模}，部署方式{部署方式，如 K8s 或虚拟机}，监控{监控现状，如 有无链路追踪和集中日志}。先读代码和表结构，然后回答：
1. 现在值不值得拆。团队、部署和监控条件不够时，直接建议先做模块化单体，并说明还缺什么。
2. 值得拆的话，按业务能力给出候选服务清单，每个写明职责、拥有的表、对外 API 和发布的事件。
3. 列出现在跨候选服务的事务和 join 查询，给出拆分后的做法（Saga、事件、快照字段、BFF 聚合）。
4. 选第一个拆出去的服务，写出迁移步骤：先在单体里隔离边界，再做数据同步，灰度切流量，最后下线旧代码；每一步都写清怎么回退。
这一步只输出方案，不改代码；拿不准的地方单独列出。
