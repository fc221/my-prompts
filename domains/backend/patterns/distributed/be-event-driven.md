## 是什么

服务之间不直接调用，生产者把消息发到消息队列，消费者按自己的节奏取出来处理。用来做异步解耦、削峰填谷和一对多通知，代价是只能做到最终一致，还要处理重复、乱序和积压。

## 适合

主流程之后的非关键步骤（下单后发券、发短信、同步到数仓）；流量突刺需要缓冲（大促时下单请求先入队，按库存服务的能力消费）；一个事件有多个下游各自处理。

## 不适合

调用方必须马上拿到结果的操作（支付前查余额、下单时校验库存），用同步 API 加超时；单体内部的模块联动，用进程内的「领域事件」；只是要跑个后台任务，用「后台任务队列」，不必为此运维一套 MQ 集群。

## 注意

消息队列通常是“至少一次”投递，消费者一定会收到重复消息，所以每个消费者都要幂等：用消息里的 eventId 或业务唯一键做去重表或唯一约束，去重记录和业务修改放在同一个事务里。

## 要点

- 选型看需求：高吞吐、分区内有序、可回放选 Kafka；灵活路由、单条确认选 RabbitMQ；事务消息、延时消息选 RocketMQ。团队已经在运维的那一个优先。
- 顺序只在同一分区（同一队列）内成立：要按订单有序，就用订单号做分区键；跨订单不保证顺序，消费者按版本号或状态机丢弃过期消息。
- 确认时机：业务处理完、数据库提交后再 ack 或提交位点；失败按指数退避重试 3–5 次，仍失败进死信队列，同时告警，并提供按 eventId 重放的工具。
- 消息体含 eventId、事件类型、版本号、发生时间、业务键和必要字段；用 JSON 或 Protobuf 并带 schema 版本，字段只增不删。
- 命名统一：主题用“业务域.实体.事件”，如 trade.order.paid、ticket.ticket.closed；消费者组按服务命名，如 points-service。
- 监控消费延迟（lag）、死信数量、处理耗时和失败率，lag 超过阈值告警；积压时先加消费者并发，分区数就是并发上限。
- 目录示例：src/messaging/producers/、src/messaging/consumers/（一个消费者一个文件，如 on_order_paid_add_points）、src/messaging/schemas/；要求发送不丢时配合「发件箱模式」。
- 过度设计的信号：同步就能完成的请求也拆成“发消息、等回调”；一个流程靠七八个消息串起来，出了问题没人说得清卡在哪一步。

## 提示词

在{项目}里用消息队列处理{场景，如 订单支付后发券和加积分}，项目用的 MQ 是{MQ 产品}。先读现有的生产者、消费者封装和配置，沿用它们。要求：
1. 主题按“业务域.实体.事件”命名，消息体含 eventId、事件类型、版本号、发生时间和{业务字段}。
2. 发送必须不丢时，先写发件箱表再投递。
3. 每个消费者幂等：用 eventId 或业务唯一键去重，去重记录和业务修改在同一个事务里。
4. 处理成功后再确认；失败按指数退避重试{重试次数}次，仍失败进死信，并打一条带 eventId 的错误日志。
5. 需要按{分区键，如 订单号}保证顺序的，用它做分区键，消费者丢弃版本号更旧的消息。
6. 加消费延迟和死信数量两个监控指标。
补测试：同一条消息投递两次只生效一次；处理抛错时不确认。最后列出改动文件和验证步骤。
