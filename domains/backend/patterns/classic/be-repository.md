## 是什么

用一组面向业务对象的方法（findById、save、按业务条件查找）把数据存取包起来，业务代码只说“取订单、存订单”，不关心底下是 SQL、ORM 还是远程服务。

## 适合

业务层要脱离数据库做单元测试；同一份数据有多个存储（主库、缓存、搜索）；聚合需要整体加载、整体保存，比如订单连同订单行一起存。

## 不适合

已经用了 ORM、业务又简单的项目，ORM 的 model 和查询构造器本身就起仓储的作用，再包一层只是转调，直接在 service 里用 ORM；报表和导出这类重查询写专门的查询类，见「读写分离模型（CQRS）」。

## 注意

仓储按聚合建，不按表建：订单和订单行共用一个 OrderRepository，订单行没有自己的仓储。方法签名里只出现领域对象和业务条件，ORM 的查询对象留在实现内部，否则调用方又会自己拼 SQL。

## 要点

- 方法用业务语言命名：findPendingByMember(memberId)、existsByOutTradeNo(no)、save(order)；通用的“传一个条件 map 进去查”会把查询逻辑漏到 service。
- 接口定义在业务层或领域层，实现放基础设施层：domain/order/order_repository 是接口，infra/persistence/order_repository_mysql 是实现。
- 查单条没找到返回空值（null 或 Optional），由业务层决定返回 404 还是走别的分支；列表查询一律带分页或上限，默认上限如 200 条。
- save 负责整个聚合：订单行的增删改在同一个事务里落库，乐观锁版本号在这里校验，冲突时抛明确的并发冲突错误，见「乐观锁与悲观锁」。
- 测试：业务层单测用内存实现（一个 map 就够），仓储实现用真实数据库跑集成测试（容器起 MySQL 或 PostgreSQL），SQL 不做 mock。
- 过度设计的信号：泛型 BaseRepository 带十几个通用方法、每张表一个仓储、仓储里出现业务 if、仓储和 ORM model 一一对应且方法全是转调。

## 提示词

为{聚合名，如 订单}写仓储。先看项目的数据访问方式（{ORM 或 SQL 工具}）和已有仓储的写法，照着来。要求：
1. 按聚合建仓储，{子对象，如 订单行}跟着聚合一起读写，不单独建仓储。
2. 接口放在业务层，方法用业务语言命名，只提供这次用到的查询（{查询需求，如 按会员查待支付订单、按外部交易号判断是否已存在}）。
3. 查不到返回空值，由调用方决定怎么处理；列表一律分页或设上限。
4. save 在一个事务里保存整个聚合并校验版本号，冲突时抛并发冲突错误。
5. 给业务层准备一个内存实现用于单测；真实实现用测试数据库跑集成测试。
