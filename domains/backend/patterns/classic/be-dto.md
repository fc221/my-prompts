## 是什么

接口收发的数据结构（请求 DTO、响应 DTO）、业务里用的对象（领域模型）和数据库映射（持久化对象）各用各的类型，在层的边界处转换。改表结构不会牵动对外接口，客户端也拿不到不该拿的字段。

## 适合

对外开放的接口和多端共用的接口；表里有敏感字段（密码哈希、成本价、内部备注）；同一资源在不同端返回的字段不同，比如后台能看订单成本，会员端看不到。

## 不适合

内部脚本、原型、只有一端调用且字段完全一致的简单增删改查，可以让 ORM 实体直接序列化，但返回字段要用白名单控制；分三套对象时内容完全一样的话，先只分“请求 / 响应”和“数据库实体”两套。

## 注意

最危险的是把请求体直接绑定到 ORM 实体再保存（批量赋值）：用户在注册请求里多传一个 role 或 balance 字段就能改掉它。请求 DTO 只列客户端允许写入的字段。

## 要点

- 三类对象：请求对象（CreateOrderRequest，只含客户端可写字段和校验规则）、响应对象（OrderResponse、OrderDetailResponse，按场景裁剪）、领域或持久化对象（Order）。
- 转换位置：请求对象在接口层转成命令或领域对象，领域对象在接口层转成响应对象；service 的参数和返回值里没有 HTTP 相关类型。
- 命名后缀全项目统一一套，如 Request / Response / Entity；VO、BO、PO、DTO 四种叫法不混用。
- 响应用白名单：数据库新增的字段默认不出现在接口里，要显式加进响应对象；金额用整数分或字符串小数，时间用带时区的 ISO 8601，见「时间、金额与 ID 格式」。
- 按场景分响应：列表项 OrderListItem 只放列表上显示的 8–10 个字段，详情 OrderDetail 再带订单行和收货地址。
- 映射代码手写，或用编译期生成的映射工具（如 Java 的 MapStruct）；字段改名时编译就报错，比运行时按字段名反射拷贝安全。
- 目录示例：src/order/api/（request/、response/、order_mapper）、src/order/domain/、src/order/persistence/，转换函数集中在 order_mapper。
- 过度设计的信号：每层一套类、字段完全一样还要来回拷贝四次。先从两套开始，出现差异再拆。

## 提示词

把{资源名，如 订单}的接口模型和领域、数据库对象分开。先列出这个资源的接口现在接收和返回的都是什么类型，标出直接序列化 ORM 实体、请求体直接绑定实体的地方。然后：
1. 每个写接口一个请求对象，只含客户端可写字段（{可写字段}）；{服务端字段，如 状态、金额、所属会员}只由服务端赋值。
2. 按场景拆响应对象：列表项、详情、{其他场景，如 后台视图}；字段用白名单，{敏感字段，如 成本价、内部备注}只出现在后台视图。
3. 转换放在接口层的 mapper 里，service 的参数和返回值里没有 HTTP 类型。
4. 命名后缀沿用项目已有的那一套。
接口返回的字段名和格式保持和现在一致；需要去掉的不该返回的字段单独列出，等我确认。最后补一条测试：请求里多传一个服务端字段时不会被写入。
