## 是什么

新服务开工前，用五个能核对的条件定语言和框架：团队现有技能、性能和并发、生态、部署和运维、招聘。结论写成一页决策记录，写明被否掉的选项和理由。

## 适合

新项目立项；从单体拆出新服务、考虑换语言；外包或新团队接手前定技术栈；让 AI 生成项目骨架前先定框架。

## 不适合

已有项目里加功能，直接沿用现有栈，看对应框架的约定条目；接口协议怎么选看「REST、GraphQL、gRPC 怎么选」；要不要拆服务看「模块化单体」「微服务拆分」。

## 注意

没有可量化的理由，就选团队已经在生产上跑熟的那套。为性能换语言之前先压测：多数业务的瓶颈在数据库和网络往返，换语言解决不了。

## 要点

- 团队技能：团队里至少 2 人在生产环境用这门语言和框架排过障、调过优，才列为首选；只有 1 人会或都没用过的，排期里加 2–4 周做样板项目和培训，排不出时间就不选。
- 性能和并发：先写下目标峰值 QPS、P99 延迟和单机资源预算。普通 CRUD 和后台管理，主流框架都够用，按团队技能选；单实例要扛上万长连接（推送、IM、网关），Go、Node.js、Rust、Java 21 虚拟线程、ASP.NET Core 都合适，同步的 Python 框架不合适；CPU 密集且 P99 要求在几十毫秒内，优先 Go、Rust、Java、ASP.NET Core，Python 和 Node.js 的 CPU 重活拆到 worker 或独立服务。
- 生态：列出必须对接的东西（支付、短信、消息队列、对象存储、国产数据库、AI 和数据处理库），逐项确认目标语言有维护中的官方 SDK 或主流库（最近一年内有发版）；机器学习和数据处理多的选 Python；政企项目、国产中间件和信创适配要求多的，Java 生态最全。
- 部署和运维：对照现有流水线、基础镜像和监控接入。要求单文件交付、镜像小、冷启动快（Serverless、边缘节点、命令行工具）选 Go 或 Rust；已有 JVM 调优和 APM 经验的继续用 Java；PHP 和 Ruby 要额外维护进程管理（PHP-FPM、Puma）和队列 worker，算进运维成本。
- 招聘：在当地招聘渠道查该语言 3–5 年经验岗位的数量和薪资，和团队预算对比；国内 Java 人最多，Go、Python、Node.js 次之，Rust、Ruby、Elixir 人少，选了就要接受更长的招人周期或内部培养。
- 框架类型：要快速做出完整业务（后台、内容站、管理系统、带用户体系）选全家桶框架（Spring Boot、Django、Rails、Laravel、NestJS、ASP.NET Core）；只做 API、网关或 BFF，团队愿意自己定结构，选轻量框架（FastAPI、Express / Fastify、Go 标准库或 Gin、Axum）。
- 收敛：同一团队的后端语言不超过 2 种；新服务和现有服务同语言时直接复用鉴权、日志、错误码、配置这些公共库，换语言就要先把这些补齐，工作量算进评估。
- 决策记录：写背景和约束、至少 2 个候选、五项条件逐条的证据（拿不到的数据写“待确认”）、结论和放弃的理由、什么情况下重新评估（如峰值超过设计值 3 倍、核心依赖停更）。

## 提示词

帮我为{项目}选后端语言和框架。业务：{业务描述}；团队现在会：{团队技术栈}；预计峰值 {峰值 QPS}，P99 延迟目标 {延迟目标}；必须对接：{外部系统}；部署在：{部署环境}。
判断条件：
{{要点}}

做法：仓库里已经有服务的，先读一遍，列出现有的语言、框架、公共库和部署方式。挑 2–3 个候选，按上面的条件逐条判断，每条写依据（团队经验、压测数据、SDK 维护情况、现有流水线、招聘情况），拿不到的数据标“待确认”，不要估。没有可量化的理由时，选团队已在生产使用的栈。
输出一页决策记录，再列出选定框架开工第一周要定下的约定：目录结构、配置和环境、错误响应格式、日志、迁移工具、测试和常用命令。
