## 是什么

服务端确认“你是谁”的实现：密码怎么存，登录成功后发会话还是令牌，令牌多久过期、怎么续期和吊销，怎么防暴力破解和撞库。对外用 Cookie、Bearer 令牌还是 API Key 看「认证方式」，这里写服务内部怎么落地。

## 适合

新系统做账号密码、短信验证码登录；老系统密码用 MD5 或明文存储，需要升级；令牌泄露后无法让用户下线。

## 不适合

登录后能做什么是授权，看「权限模型」；对外接口的认证方式选型看「认证方式」；接入企业单点登录时用成熟的 OIDC 库或身份服务，协议本身不自己实现。

## 注意

自己设计加密方案是最大的坑：MD5、SHA-256 加盐都太快，库一泄露很快就被暴力破解，密码只能用专门的慢哈希。其次，无状态 JWT 签发后收不回，改密码、封号后旧令牌照样能用，所以访问令牌要短期，配合服务端可吊销的刷新令牌。

## 要点

- 密码哈希：Argon2id（内存至少 19 MiB、迭代 2、并行 1）或 bcrypt（cost 至少 10，推荐 12，注意只取前 72 字节）；用库自带的 verify 比较；哈希串里自带算法和参数，参数升级后在用户下次登录成功时重新哈希。
- 会话方案（Web 后台、同域前端）：会话存 Redis，会话 ID 至少 128 位随机；Cookie 设 HttpOnly、Secure、SameSite=Lax；登录成功后更换会话 ID，防会话固定；闲置 30 分钟、绝对 12 小时过期。
- 令牌方案（App、小程序、跨域调用）：访问令牌 15 分钟，刷新令牌 7–30 天、服务端只存哈希、每次使用后轮换；旧刷新令牌再次出现时作废整个令牌族；改密码、封号、主动退出时吊销该用户全部刷新令牌。JWT 校验固定算法（拒绝 alg 为 none），并校验 exp、iss、aud。
- 防暴力破解：同一账号 15 分钟内失败 5 次后要求图形验证码或逐次延迟，同一 IP 另设阈值；失败提示统一为“账号或密码错误”，不暴露账号是否存在；频率限制的配置见「限流与配额」。
- 短信验证码：6 位数字，5 分钟有效，校验失败 5 次即作废，同一手机号 60 秒内只发一次、每天最多 10 条，用过立即失效；服务端只存哈希或带过期时间的 Redis 键。
- 敏感操作（改密码、换绑手机、提现、导出全部会员）要求重新输入密码或验证码；后台管理员账号强制 TOTP 二次验证。
- 第三方登录（如微信）只信任服务端用 code 换来的 openid、unionid，客户端直接传来的用户标识一律不认；绑定关系单独建表。
- 登录事件：成功、失败、登出、刷新令牌、异地登录都记录 user_id、IP、设备和 trace_id，密码和令牌原文不记录。

## 提示词

检查并加固{项目}的登录认证，登录方式有{账号密码 / 短信验证码 / 第三方登录}，客户端是{Web 后台 / App / 小程序}。
1. 盘点：找出密码哈希算法和参数；会话或令牌的生成、存储、过期和吊销方式；登录失败的处理和频率限制；验证码规则；登录日志。标出用 MD5 或 SHA 系列存密码、令牌无法吊销、刷新令牌明文存储或不轮换、失败提示能看出账号是否存在的地方。
2. 按规则改：密码改用 Argon2id 或 bcrypt，旧哈希在用户下次登录成功时迁移；Web 用 HttpOnly、Secure、SameSite Cookie 会话，登录后更换会话 ID；App 用 15 分钟访问令牌加可轮换、可吊销的刷新令牌；加失败锁定和验证码；短信验证码按 6 位、5 分钟、5 次、60 秒间隔执行；敏感操作二次验证；记录登录事件。
3. 补测试：错误密码 5 次后要求验证码；改密码后旧刷新令牌失效；刷新令牌重放时整族作废。
4. 汇报：改动文件、旧密码哈希和旧令牌的过渡方案、测试结果。
