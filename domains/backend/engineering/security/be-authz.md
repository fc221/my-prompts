## 是什么

认证之后决定“你能做什么、能看哪些数据”。功能权限用角色和权限点（RBAC）管：谁能审批报销、谁能导出订单；数据权限按范围管：本人、本部门、本部门及下级、全部；带条件的规则（金额 5000 元以上要财务总监审批）按属性判断（ABAC）。

## 适合

后台管理、审批流、工单系统的角色和菜单权限；同一张表不同人看到不同数据；排查越权漏洞，比如改一下 URL 里的 ID 就能看到别人的订单。

## 不适合

确认用户身份看「登录认证」；租户之间的隔离看「多租户数据隔离」；开放平台上第三方应用的授权范围看「认证方式」。

## 注意

前端隐藏按钮不算权限控制。最常见的漏洞是越权访问（IDOR）：接口只校验了登录，没校验这张工单是否在当前用户的可见范围内，改个 ID 就能读写。每个按 ID 访问资源的接口都在服务端校验归属。

## 要点

- 模型：用户、角色、权限点三层，一个用户可以有多个角色；权限点按 资源:操作 命名，如 order:export、expense:approve、ticket:assign；菜单和按钮是否显示由权限点推出来，不另建一套。
- 默认拒绝：没有显式授予就拒绝；新增路由必须声明所需权限点，CI 扫描出未声明权限的路由直接失败。
- 校验位置：功能权限在入口用注解或中间件统一校验（Spring Security @PreAuthorize、NestJS Guard、FastAPI 依赖项）；数据权限下沉到查询，由仓储层按当前用户的数据范围追加条件（如 dept_id IN 可见部门列表），而不是查出全部再在内存里过滤。
- 资源归属：按 ID 读写单个资源时，查询条件同时带上归属（WHERE id = ? AND tenant_id = ? AND 数据范围条件）；查不到统一返回 404，不暴露资源是否存在；能看但无权执行该操作的返回 403。
- 条件规则：审批金额阈值、只有草稿状态的报销单能改、只能处理分配给自己的工单，这类规则集中写在领域服务或策略类里并配单元测试；规则多且多处共用时再引入策略引擎（Casbin、OPA）。
- 生效和缓存：用户的权限集合可以缓存在会话或 Redis，角色变更时主动失效；令牌里只放用户 ID 和角色 ID，完整权限列表不放进 JWT，否则改了权限要等令牌过期才生效。
- 特殊账号：超级管理员也通过权限点授权，代码里不写死某个用户 ID；权限的授予和回收、批量导出、删除这类高危操作写审计记录。
- 测试：每个接口准备有权限、无权限、跨部门、跨租户四类用例，分别断言 200、403、404、404。

## 提示词

检查{项目}的权限控制，现有角色有{角色列表，如申请人、部门经理、财务、管理员}，数据范围规则是{如部门经理看本部门及下级}。
1. 盘点：列出所有路由和各自的权限校验方式，标出只校验登录、没校验权限点的；按 ID 访问资源却不校验归属的（越权风险）；在内存里过滤数据权限的；前端隐藏了按钮但后端没拦的；硬编码用户 ID 判断的。
2. 按规则改：权限点按 资源:操作 命名并集中定义；每个路由声明所需权限点，默认拒绝；数据范围条件由仓储层统一追加；按 ID 访问时带归属条件，查不到返回 404、无权操作返回 403；{条件规则，如报销金额超过 5000 元需财务总监审批}集中写在策略类；角色变更时失效权限缓存；权限变更和高危操作写审计记录。
3. 补测试：每个接口覆盖有权限、无权限、跨部门、跨租户四类用例。
4. 汇报：路由权限清单、发现的越权点、改动文件、测试结果。
