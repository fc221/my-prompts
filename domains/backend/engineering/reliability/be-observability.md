## 是什么

指标回答“现在好不好”：请求量、错误率、耗时分布、队列积压；链路追踪回答“慢在哪一段”：一次下单经过网关、订单、库存、支付，各花了多久。两者和日志用 trace_id 串在一起。

## 适合

服务上线前补监控和告警；接口变慢却不知道慢在哪个下游；给服务定可用性目标；大促前核对容量。

## 不适合

单个请求的详细上下文看「结构化日志」；健康检查端点看「健康检查与优雅停机」。

## 注意

把用户 ID、订单号、原始 URL 这种取值无限的字段放进指标标签，时间序列数量会爆炸，监控系统先被拖垮。标签只放取值有限的维度：路由模板、方法、状态码。

## 要点

- 覆盖面：每个服务入口和每个下游依赖都记三样，请求数、错误数、耗时直方图；连接池、线程池、队列这类资源记使用量、排队数和拒绝数。
- 命名（Prometheus 习惯）：snake_case，带单位后缀，计数器以 _total 结尾，如 http_server_requests_total、order_created_total、db_pool_active_connections、job_duration_seconds；耗时统一用秒。
- 标签：route 用路由模板（/orders/:id），加 method、status；单个指标的标签组合控制在 1000 以内；user_id、order_no、trace_id 不做标签。
- 耗时用直方图：按延迟目标设桶（如 0.05、0.1、0.25、0.5、1、2.5、5 秒），看 p50、p95、p99；平均值会掩盖长尾，面板上不单独用平均值。
- 业务指标：再记几个直接反映业务健康的计数，如下单数、支付成功率、待审批积压数；业务指标突然下跌，往往比错误率更早暴露问题。
- 链路追踪：用 OpenTelemetry SDK 自动埋点 HTTP、数据库、Redis、消息队列，跨服务通过 W3C traceparent 头传播；span 名用 方法 + 路由模板（GET /orders/:id）；默认按比例采样 5%–10%，错误和慢请求用尾部采样全部保留。
- 告警：按用户感受定目标，如“下单接口 99.9% 的请求在 1 秒内成功返回”，按错误预算的消耗速度告警，CPU 瞬时尖刺不告警；每条告警写明含义、影响和处理步骤，长期没人处理的告警删除。
- 互相跳转：日志带 trace_id 和 span_id；直方图打开 exemplar，从耗时尖刺直接跳到对应的 trace。

## 提示词

为{项目}补齐指标和链路追踪，监控用{Prometheus 加 Grafana / 云厂商监控}，追踪用 OpenTelemetry 上报到{追踪后端}。
1. 盘点：列出服务现有的指标（名称、标签）、追踪接入情况和告警；标出标签里有用户 ID 或原始 URL 的指标、用平均值看耗时的面板、没有监控的下游依赖（数据库、Redis、{下游服务}）。
2. 按规则改：入口和每个下游记请求数、错误数、耗时直方图，snake_case 加单位后缀；标签只用路由模板、方法、状态码；连接池和队列记使用量和积压；加{业务指标，如下单数、支付成功率}；接入 OpenTelemetry 自动埋点并用 traceparent 传播，采样 10%，错误和慢请求全保留；日志附 trace_id 和 span_id。
3. 告警：为{核心接口}定可用性和延迟目标，按错误预算消耗速度告警，每条附处理步骤。
4. 汇报：新增指标清单、面板查询语句、告警规则文件，并用一次真实请求展示完整的追踪链路。
