## 是什么

把耗时或可以延后的工作（发短信、生成报表、同步库存到第三方、解析导入的 Excel）从请求里拿出来，放进队列由后台 worker 执行。请求只负责入队并立即返回；失败的任务按规则重试，最终失败的进死信队列等人处理。

## 适合

请求里要调慢的第三方接口；导入导出、批量通知；需要削峰的写入（大促期间的积分发放）；“下单 30 分钟未支付自动关闭”这类按单延迟执行的任务。

## 不适合

服务之间的业务事件分发看「事件驱动与消息队列」；按固定时刻执行的任务看「定时任务」；对外暴露的“提交后查进度”接口看「长任务异步化」。

## 注意

绝大多数队列只保证“至少一次”投递：worker 处理完还没确认就重启，任务会再执行一次，所以每个任务处理器都必须幂等。另一个坑是在数据库事务提交前入队，worker 先跑起来，查不到还没提交的数据。

## 要点

- 幂等：任务带唯一 ID 或业务键（如 points_grant:<订单号>），处理前检查是否已完成，靠数据库唯一约束兜底；重复执行时直接按成功返回。
- 入队时机：事务提交之后再入队（after commit 钩子），或把任务写进同库的发件箱表、由转发器投递，见「发件箱模式」。
- 载荷：只放 ID 和必要参数（order_id、tenant_id、trace_id），worker 执行时重新读取最新数据；载荷带格式版本号，便于升级时新旧兼容。
- 重试：可重试的错误按退避间隔重试（如 10 秒、1 分钟、5 分钟、30 分钟、2 小时）最多 5 次；数据不存在、参数非法这类不可能成功的错误直接标记失败；超过次数进死信队列并告警，后台提供重放按钮。
- 超时和确认：每个任务设执行超时；处理完成后再确认（Celery 的 acks_late，RabbitMQ、SQS 的手动确认），可见性超时大于任务最长执行时间；worker 停机时把未完成的任务还回队列。
- 隔离：按优先级和耗时拆队列（critical、default、bulk），导出报表这类慢任务不挡住验证码短信；每个队列单独设并发，调第三方的队列并发不超过对方的限流额度。
- 选现成的：Java 用 Spring 的消息集成或 JobRunr，Python 用 Celery 或 RQ，Ruby 用 Sidekiq，Node 用 BullMQ，Go 用 Asynq 或 River；PostgreSQL 项目量不大时可以直接用一张表加 SKIP LOCKED 当队列。
- 监控：队列长度、最老任务的等待时间、处理耗时、失败率和死信数量；最老任务等待超过阈值（如 5 分钟）告警。

## 提示词

把{项目}里的{耗时操作，如下单后发短信、导出订单报表}改成后台任务，或检查现有任务队列；队列用{Redis / RabbitMQ / Kafka / 数据库表}，语言和框架是{语言和框架}。
1. 盘点：列出所有入队位置和任务处理器，标出事务提交前就入队的、载荷里放整个对象的、处理器不幂等的、没有重试上限或对所有错误都重试的、没有死信和告警的、快慢任务挤在同一个队列的。
2. 按规则改：提交后入队或走发件箱；载荷只放 ID、tenant_id、trace_id 和格式版本号；处理器用业务键加唯一约束保证幂等；可重试错误按退避最多 5 次，不可重试错误直接失败；超限进死信并告警；处理完再确认，设执行超时；按 critical、default、bulk 拆队列并设并发。
3. 补测试：同一任务执行两次结果不变；模拟第三方失败后按退避重试，最终进入死信。
4. 汇报：任务清单（名称、队列、重试策略、幂等键）、改动文件、测试结果和新增的监控指标。
