## 是什么

按层次组织后端测试：大量快速的单元测试覆盖业务规则，适量的集成测试用真实数据库和中间件覆盖仓储和接口，少量契约测试和端到端测试覆盖服务之间的约定。目标是改代码时心里有底，CI 几分钟内给出结论。

## 适合

新项目定测试结构；老项目没有测试、改一处坏一处；mock 太多，测试全绿上线却出错；CI 太慢没人愿意等。

## 不适合

前端测试看「前端测试分层」；压测和容量评估单独安排，不放进每次提交的 CI。

## 注意

用 H2、SQLite 这类内存库代替生产的 MySQL 或 PostgreSQL 做集成测试，SQL 方言、锁和事务行为都不一样，测试通过不代表线上能跑。涉及数据库的测试用同版本的真实数据库（Testcontainers）。

## 要点

- 单元测试：覆盖领域规则和应用服务的分支（库存不足、积分不够、审批金额阈值、非法的状态流转），不连数据库和网络，外部依赖用手写的假实现或 mock；单个用例毫秒级，全部单元测试 1 分钟内跑完。
- 集成测试：仓储、迁移、事务和锁、HTTP 接口用 Testcontainers 起同版本的 MySQL、PostgreSQL、Redis、消息队列；每个测试的数据互相独立（事务回滚或测试前清表），可以并行、可以任意顺序运行。
- 迁移：CI 从空库执行全部迁移后再跑集成测试，保证新环境能从零搭起来。
- 外部服务：第三方 HTTP 用 WireMock、MockServer 或框架自带的桩服务模拟，覆盖成功、超时、5xx、返回格式异常；测试里不调用真实的支付和短信。
- 契约测试：服务之间的接口用消费者驱动契约（Pact）或基于 OpenAPI 的契约校验，提供方在 CI 里验证没有破坏消费方，见「契约优先」。
- 端到端测试只留少量核心链路（下单到支付成功、报销提交到审批通过），在预发布环境运行，不阻塞每次提交。
- 可重复：时间、随机数、ID 生成器通过注入换成固定值（如固定时钟 2026-10-29T08:00:00Z）；等待异步结果用带超时的轮询而不是 sleep；测试数据用构造器或工厂生成有意义的数据（如“金卡会员，积分 1200”），不共用一份大夹具。
- 命名和覆盖：用例名写清场景和期望，如 deduct_stock_fails_when_quantity_insufficient；覆盖率看领域层和应用层（目标 80% 以上），getter 和框架代码不为凑数而测；修 bug 先写一个能复现它的失败用例。

## 提示词

为{项目}整理测试分层，语言和框架是{语言和框架}，数据库是{MySQL / PostgreSQL}。
1. 盘点：按单元、集成、端到端统计现有测试的数量和耗时；标出用内存库代替真实数据库的、mock 了仓储却想测 SQL 逻辑的、依赖执行顺序或共享数据的、用 sleep 等待的、调用真实第三方的测试；找出{核心模块，如订单、库存、积分}里没有测试覆盖的业务分支。
2. 按规则改：业务规则补单元测试，不连外部依赖；仓储和接口的集成测试改用 Testcontainers 起同版本数据库，数据互相独立；CI 从空库跑迁移；第三方用桩服务模拟成功、超时、5xx；时间和 ID 注入固定值；用工厂生成测试数据。
3. CI 分阶段：单元测试每次提交跑，集成测试每个合并请求跑，端到端测试在预发布环境跑。
4. 汇报：分层统计改前改后对比、新增和改造的测试、本地运行命令、CI 耗时。
