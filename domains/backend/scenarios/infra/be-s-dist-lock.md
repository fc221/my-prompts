## 是什么

多个服务实例之间的互斥：同一时刻只允许一个实例执行某段逻辑，比如结算某门店某天的账、重建同一份缓存、处理同一张工单。锁要能自动过期防止死锁，持有者要能证明自己仍然持有。

## 适合

定时任务部署多实例但只能跑一份、缓存重建只放一个请求、对第三方的非幂等调用要串行、同一用户的操作要串行。

## 不适合

同一张表里的行级并发用「乐观锁与悲观锁」的条件更新或 FOR UPDATE，正确性更好保证；扣库存这类一条原子操作就能表达的不加锁；定时任务单实例执行也可以直接用调度器的集群模式，见「定时任务」。

## 注意

Redis 锁是一份有过期时间的租约，不是严格互斥：持锁进程 GC 停顿、网络卡住超过过期时间，锁就会被别人拿走，两边同时执行。Redis 主从切换时，刚写进主库的锁还没同步到从库也会丢。所以被保护的写入必须自己能拒绝过期的持有者（防护令牌或条件更新）；要严格互斥用 etcd 或 ZooKeeper。

## 要点

- 先问要不要：单实例部署用进程内锁；同一行数据用数据库锁；只有跨实例、跨资源的互斥才用分布式锁。
- 加锁：SET lock:settle:<门店ID>:<营业日> <随机 UUID> NX PX 30000，返回 OK 才算拿到；随机值标识持有者，过期时间取业务耗时 P99 的 3 倍以上。
- 释放：用 Lua 比对后删除，脚本是 if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end；放在 finally 里，释放失败只记日志，等它自然过期。
- 续期：可能超过过期时间的任务，拿到锁后起一个定时器，每过 1/3 过期时间（10 秒）检查值仍是自己就 PEXPIRE 续回 30 秒；进程挂了续期随之停止，锁最多 30 秒后释放。Redisson 的 lock() 不传 leaseTime 时就是这种看门狗行为，默认 30 秒。
- 拿不到锁：按场景选，立即返回“正在处理”（409），或每 100ms 重试最多 3 秒，不无限等待；要可重入时用 Hash 记录持有者和重入次数，能不重入就不重入。
- 防护令牌：加锁成功后 INCR lock:token:<资源> 得到单调递增的令牌，写下游时带上，下游执行 UPDATE … SET …, last_token = ? WHERE id = ? AND last_token < ?，旧持有者的令牌更小，被拒绝。
- 严格互斥：etcd 用带 TTL 的 lease（如 10 秒）加 KeepAlive，concurrency 包的 Mutex 加锁，锁键的 revision 可以直接当防护令牌；ZooKeeper 用临时顺序节点，会话断开锁自动释放。Redlock（多个独立 Redis 节点取多数）仍依赖时钟假设，不能替代防护令牌。
- 监控：记录等锁时长、持锁时长、获取失败次数和续期失败次数；持锁时长接近过期时间时告警。

## 提示词

在{项目}里给{要互斥的操作，如门店日结、同一工单的处理}加分布式锁：先确认量级和必要性——部署实例数、单次执行耗时 P99、拿不到锁时该等还是直接返回、同时执行两份的后果；单实例或能用数据库条件更新解决的，直接说明不加分布式锁。再按以下设计：
1. 锁键带业务含义，SET 锁键 随机值 NX PX，过期时间取 P99 耗时的 3 倍。
2. 释放用 Lua 比对值后删除，放在 finally。
3. 可能超时的任务用看门狗每 1/3 过期时间续期，进程退出即停止续期。
4. 拿不到锁按场景立即返回 409，或每 100ms 重试最多 3 秒。
5. 被保护的写入带 INCR 生成的防护令牌，下游用条件更新拒绝旧令牌。
6. 要求严格互斥时改用{etcd / ZooKeeper}。
最后给出压测和对账方法：20 个实例同时抢锁执行 1000 次，断言任一时刻只有一个持有者；注入 40 秒停顿让锁过期，确认旧持有者的写入被令牌拒绝；核对业务结果没有重复执行，如每个门店每天只有一条日结记录。
