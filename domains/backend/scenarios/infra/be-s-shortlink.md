## 是什么

把很长的落地页地址换成 /s/APnamX 这样的短地址，访问时服务端查到原地址再跳转过去。要解决三件事：短码怎么生成且不重复、跳转用 301 还是 302、海量的跳转读请求怎么扛。

## 适合

短信和推送里的营销链接、门店物料上的二维码、分享链接、带渠道参数的推广链接。

## 不适合

只在站内使用的长链接用不着短链；带登录态、优惠码这类敏感参数的地址不要做成短链（短码能被枚举），改用一次性票据。

## 注意

301 是永久重定向，浏览器和中间代理会缓存，之后的访问不再经过你的服务：点击统计会漏，改目标地址也不生效。要统计、可修改、会过期的短链都用 302。另一个坑是自增 ID 直接转 62 进制，短码是连续的，别人顺着就能遍历出你所有的链接，对外的短码要先打乱。

## 要点

- 量级：每天新生成几千条、跳转几百 QPS，一张表加 Redis 缓存就够；日生成千万级、跳转几万 QPS 才需要号段发号和多级缓存。
- 表：short_link(id BIGINT, code VARCHAR(10) 唯一, target_url VARCHAR(2048), url_hash CHAR(64) 索引, creator_id, channel, expire_at, status, created_at)。
- 方式一，自增转 62 进制：从号段取 ID（见「订单号与分布式 ID」），先乘一个与 62 互质的大奇数再对 62^6 取模（可逆、不冲突），再转 Base62（0-9a-zA-Z）；如 10000123 直接转是 FXuj，打乱后是 APnamX；6 位约 568 亿个，ID 超过 62^6 时改为 7 位。
- 方式二，哈希：对原地址加盐算 MurmurHash3，取 6–7 位 Base62；冲突时在原地址后追加计数重算，code 唯一约束兜底；同一地址天然得到同一短码，代价是要处理冲突。
- 去重：同一创建者、同一渠道重复生成同一地址时，按 url_hash 查到已有短码直接返回；不同渠道要分开统计就各生成一条。
- 跳转：GET /s/:code 依次查进程内缓存（1 万条、TTL 10 分钟）、Redis、数据库，返回 302 和 Location；不存在的码缓存空值 60 秒，防枚举的做法见「缓存穿透、击穿与雪崩」；过期或下架返回 410 和一个说明页。
- 统计：跳转时只往队列写一条点击事件（code、时间、UA、IP、Referer），异步聚合成按天、按渠道的报表，跳转路径上不写库；独立访客数用 HyperLogLog。
- 安全：目标地址只允许 http 和 https 协议，写入前做恶意网址检测，可配置域名白名单；单 IP 生成频率限制，短码不少于 6 位。

## 提示词

在{项目}里实现短链服务：先确认量级——每天新生成多少条、跳转峰值 QPS、要不要点击统计、能否修改目标地址和设置过期；日生成几千条、跳转几百 QPS 时，一张表加 Redis 缓存就够。再按以下设计：
1. 建 short_link 表，code 唯一，带 target_url、url_hash、channel、expire_at、status。
2. 短码用{自增转 62 进制 / 哈希}：自增方案从号段取 ID，乘与 62 互质的大奇数对 62^6 取模后转 Base62；哈希方案对原地址加盐取 MurmurHash3 转 Base62，冲突追加计数重算。
3. GET /s/:code 按进程内缓存、Redis、数据库三级查，不存在的码缓存空值 60 秒；需要统计或可修改的返回 302，只有永久不变且不统计的才用 301；过期返回 410。
4. 点击事件异步写队列再聚合，跳转路径不写库。
5. 目标地址只允许 http 和 https，做恶意网址检测，单 IP 限制生成频率。
最后给出压测和对账方法：用 1000 万个随机地址生成短码，断言无冲突；按 80% 热点码、20% 不存在码的比例压跳转，测 P99 和数据库 QPS；每天核对点击事件条数与报表合计一致。
