## 是什么

少量库存在固定时刻开卖，瞬间流量是平时的成百上千倍，绝大多数请求注定抢不到。目标是不超卖、不少卖、系统不被打垮，办法是把无效请求挡在越外层越好：前端限流、网关限流、Redis 预扣、队列异步下单，四层逐级削峰。

## 适合

整点限量抢购、门店爆品限时价、会员日一元购、优惠券整点开抢。

## 不适合

库存充足、只是流量大的大促下单，走常规下单链路加「缓存策略」「限流与配额」；库存有具体身份（座位、时段）的看「抢票与库存锁定」；库存几百件、峰值几百 QPS，一条 UPDATE sku_stock SET qty = qty − 1 WHERE sku_id = ? AND qty >= 1 加订单唯一约束就够，不用四层。

## 注意

Redis 预扣成功不等于下单成功：异步下单失败、用户超时未支付，都要把库存还回 Redis，否则活动结束还剩货（少卖）。“先 GET 库存再 DECR”两步之间会被并发穿过去，判断限购、判断库存、扣减、记录用户必须在一条 Lua 脚本里原子完成。库存以数据库为准，活动结束后要对账。

## 要点

- 量级：有效请求最多等于库存数，其余都要挡掉；按在线人数乘点击频率估峰值 QPS，再决定上几层。
- 前端：开抢前按钮置灰，倒计时按服务端时间校准；点击后按钮锁定 3 秒；活动页静态化放 CDN；秒杀下单地址开抢时才下发一次性令牌，脚本没法提前刷。
- 网关：按 SKU 做令牌桶（每秒放行约库存的 10 倍），按用户每秒 1 次、按 IP 每秒 5 次；超出直接返回 429 和“排队人数较多”，不进业务服务。
- Redis 预扣：活动前把库存预热到 seckill:stock:<活动ID>:<SKU>；Lua 里依次 SISMEMBER seckill:buyers:<活动ID>:<SKU> 判断已抢过（返回 2）、GET 库存小于等于 0 返回 0、否则 DECR 库存并 SADD 用户返回 1；售罄后在进程内存打标记，后续请求不再访问 Redis。
- 队列下单：预扣成功后发消息（活动 ID、SKU、用户 ID、请求 ID），立即返回“抢购成功，订单生成中”；消费者按数据库能承受的并发写库，执行条件扣减，订单表 (activity_id, user_id) 唯一；客户端凭请求 ID 每 1 秒轮询结果，最多 30 秒。
- 回补：消费者下单失败，或订单 15 分钟未支付被关闭（见「订单超时取消与延迟任务」），执行 INCR 回补 Redis 库存并 SREM 用户；回补按订单号记录，只做一次。
- 防刷：开抢前校验资格（实名、会员等级、风控分），同一设备、同一收货地址限购；同一用户的重复请求被 Lua 里的已抢集合挡住。
- 隔离：秒杀服务、Redis、队列和常规下单链路分开部署；Redis 不可用时直接返回“活动太火爆”，不回落到数据库。

## 提示词

在{项目}里实现{活动名}秒杀：先确认量级——参与 SKU 数、每个 SKU 库存、预估峰值 QPS、限购规则和支付时限；库存几百、峰值几百 QPS 时只用数据库条件扣减加唯一约束，说明不上全套。再按以下设计：
1. 前端：开抢前按钮置灰，倒计时按服务端时间校准，下单地址开抢时才下发一次性令牌。
2. 网关：按 SKU 令牌桶、用户每秒 1 次限流，超出返回 429。
3. Redis 预扣：活动前预热库存，一条 Lua 脚本原子完成限购判断、库存判断、扣减和记录用户，售罄后打进程内标记。
4. 队列异步下单：预扣成功发消息并返回生成中，消费者条件扣减数据库库存，(activity_id, user_id) 唯一；下单失败或超时未支付回补 Redis 库存，按订单号只回补一次。
最后给出压测和对账方法：按 10 倍预估峰值压测，断言订单数不超过库存且没有一人多单；活动结束核对 Redis 剩余 + 已下单 + 已回补 = 初始库存，数据库库存与订单数一致。
