## 是什么

订单从发起支付到确认到账的整条链路：创建支付单、调渠道下单、接收异步通知、主动查单补偿、关单和退款，以及每天和渠道账单逐笔核对。目标是每一笔钱在本地和渠道的状态一致，有差异能自动发现。

## 适合

接入第三方支付渠道的订单支付、充值和退款；多个渠道聚合收款；门店收银和线上商城共用一套支付服务。

## 不适合

账户之间的余额划转看「转账与余额」；订单超时关闭本身看「订单超时取消与延迟任务」；收发回调的签名、重试规范看「Webhook 设计」。

## 注意

只认渠道的异步通知和主动查单结果，前端跳回来的“支付成功”页只能当提示，不能据此发货。通知会重复、会乱序、也会丢：处理按支付单号加状态条件更新保证幂等，丢通知靠主动查单补，最后靠日终对账兜底。

## 要点

- 量级：日均几百笔时，对账可以先做成每日脚本加人工核对；但支付单状态机、幂等和主动查单从第一天就要有。
- 表：payment(pay_no 唯一, order_no, channel, amount 分为单位的 BIGINT, status, channel_trade_no, paid_at, refunded_amount)，payment_notify 存每次通知原文，refund(refund_no 唯一, pay_no, amount, status)；同一订单可以有多笔支付单（换渠道重付）。
- 状态机：只允许 待支付 → 支付中 → 成功 / 失败 / 已关闭，推进一律写成 UPDATE payment SET status = 'SUCCESS', … WHERE pay_no = ? AND status IN ('PENDING', 'PAYING')，影响 0 行说明处理过，直接返回成功应答。
- 回调：先验签，再核对金额、商户号与支付单一致；在本地事务里推进支付单和订单（UPDATE orders … WHERE order_no = ? AND status = 'UNPAID'），“已支付”事件走「发件箱模式」；处理完按渠道要求返回成功应答，异常返回失败让渠道重试。
- 重复支付：订单已被另一笔支付单付过，新到的成功通知不覆盖订单，生成自动退款单原路退回。
- 主动查单和关单：创建支付单后在 1、3、5、10、30 分钟查渠道订单状态补掉单；超过支付时限先调渠道关单接口，成功后再关本地单，避免本地关了用户又付成功。
- 退款：累计退款用条件更新保证不超过实付，UPDATE payment SET refunded_amount = refunded_amount + ? WHERE pay_no = ? AND refunded_amount + ? <= amount；退款同样走通知加查询两条路。
- 日终对账：T+1 下载渠道对账单，按 channel_trade_no 与本地成功的支付单、退款单逐笔比对金额和状态，分为一致、长款（渠道有本地无，多为掉单）、短款（本地成功渠道无）、金额不符四类；差异写 recon_diff 表，掉单自动补单，其余转人工并告警；23:59 支付、次日到账的跨日单放到下一天再比一次。

## 提示词

在{项目}里实现{支付渠道}的支付与对账：先确认量级——日支付笔数、接入几个渠道、有没有退款和部分退款、同一订单能否多次发起支付；日均几百笔时对账可以先做每日脚本加人工核对，但状态机和幂等必须有。再按以下设计：
1. 建 payment、payment_notify、refund 表，金额用分为单位的整数，pay_no 唯一。
2. 状态只按 待支付 → 支付中 → 成功 / 失败 / 已关闭 推进，全部用带原状态的条件更新，影响 0 行视为已处理。
3. 回调先验签、核对金额和商户号，本地事务推进支付单和订单，事件走发件箱；订单已被别的支付单付过就自动原路退款。
4. 创建后在 1、3、5、10、30 分钟主动查单，超时先调渠道关单再关本地单。
5. 累计退款用条件更新保证不超过实付。
最后给出压测和对账方法：同一通知并发重放 50 次，断言只入账一次；模拟丢通知，确认查单能补上；写 T+1 对账任务逐笔比对，输出一致、长款、短款、金额不符四类，差异入表并告警。
