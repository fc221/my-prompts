## 是什么

给订单、支付单、工单生成全局唯一的 ID 和对外单号。内部主键要唯一、趋势递增（对 InnoDB 聚簇索引友好）；对外单号还要能看出日期、方便客服报读，并且不暴露每天的单量。

## 适合

分库分表后各库自增不再全局唯一；多个服务、多个机房同时生成单号；单号里要嵌入日期、业务线或分片信息。

## 不适合

单库单表、日单量几万以内：主键用自增 BIGINT，对外单号用日期加当日序列，见「表设计约定」；分片键和基因法的选择看「读写分离与分库分表」；19 位 ID 传给前端的精度问题看「时间、金额与 ID 格式」。

## 注意

雪花算法依赖本机时钟和唯一的机器号：NTP 回拨、虚拟机迁移让时钟倒退，或两台实例拿到同一个机器号，都会发出重复 ID。机器号必须由中心分配并带租约，时钟倒退要拒绝发号。对外单号用连续序列，别人隔天各下一单就能算出你的日单量。

## 要点

- 选型：单库自增够用就用自增；应用侧生成、不依赖数据库时用 UUIDv7（128 位、时间有序，PostgreSQL 18 起内置 uuidv7()）；要 64 位整数且每秒发号上万时用雪花或号段。
- 雪花布局：1 位符号 + 41 位毫秒时间戳（自定义纪元如 2024-01-01，约可用 69 年）+ 10 位机器号（1024 个）+ 12 位序列（每毫秒 4096 个）；同一毫秒序列用完就等到下一毫秒。
- 机器号：启动时用 SET worker:<编号> <实例ID> NX EX 60 抢占一个空闲编号，每 20 秒续期，续期失败立即停止发号；容器环境不用 IP 末段推算机器号。
- 时钟回拨：记录上次发号的毫秒数，当前时间更小时，差 5ms 以内等待追上，超过就拒绝发号、告警并把实例摘出负载均衡。
- 号段模式：表 id_segment(biz_tag, max_id, step, version)，取号执行 UPDATE id_segment SET max_id = max_id + step WHERE biz_tag = 'order'，再读出 max_id，在内存里发放 (max_id − step, max_id]；step 取 10–30 分钟的用量，当前段用掉 20% 时异步预取下一段，数据库短暂不可用也能撑过去；重启丢弃没发完的号，ID 不连续是正常的。
- 对外单号：SO + yyyyMMdd + 2 位业务线 + 用户 ID 后 4 位 + 6 位序列 + 1 位校验码，如 SO20261029 01 7321 004518 6；序列用 INCRBY order:seq:<日期> 加 1–7 的随机步长，键 48 小时过期；用户 ID 后 4 位就是基因，只凭单号也能定位分片。
- 存储和校验：order_no VARCHAR(32) 唯一索引，主键仍用 BIGINT；校验码按位加权取模，客服录错一位当场能发现，格式不对的查询直接返回 404，不查库。
- 验证：单实例 8 线程各发 100 万个 ID 放进集合断言无重复且趋势递增；把时钟调回 1 秒确认拒绝发号；两个实例同时启动确认机器号不同。

## 提示词

在{项目}里实现订单号与分布式 ID：先确认量级——{日单量}、峰值每秒发号数、是否分库分表、实例数和部署方式（容器还是固定机器）；单库且日单量几万以内时，主键用自增、单号用日期加序列就够，直接说明不上发号器。再按以下设计：
1. 内部主键用{雪花 / 号段}：雪花按 41 位毫秒 + 10 位机器号 + 12 位序列，机器号用 SET NX EX 60 抢占并每 20 秒续期，时钟回拨 5ms 内等待、超过拒绝发号并告警；号段用 id_segment 表，step 取 10–30 分钟用量，用掉 20% 预取下一段。
2. 对外单号为 {单号前缀} + 日期 + 业务线 + 用户 ID 后 4 位 + 随机步长序列 + 校验码，order_no 唯一索引，格式不对直接 404。
3. ID 在 JSON 里一律以字符串返回。
最后给出压测和对账方法：多线程发 1000 万个 ID 断言无重复、趋势递增；模拟时钟回拨和两个实例抢同一机器号；每天抽查订单表 order_no 唯一、校验码全部正确。
