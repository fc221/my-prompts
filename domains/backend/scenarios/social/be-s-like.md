## 是什么

记录“谁赞了什么”，并展示“有多少人赞”。这是两份数据：点赞关系（用户加对象，要能查我赞没赞、能取消）是事实，计数是从关系派生出来的展示数据，允许几秒延迟。难点是热门内容的计数写入集中，以及列表页要批量查已赞状态。

## 适合

帖子、评论、商品评价的点赞和收藏；文章阅读数、视频播放数；门店评价的“有用”投票。

## 不适合

要按数量排名的看「排行榜」；库存、余额这类必须准确的数量不能用最终一致的计数，见「转账与余额」。

## 注意

关系表靠唯一约束保证一人一赞，计数只在关系真的变化（插入或删除影响 1 行）时才加减，否则用户连点几下数就被刷高。直接在内容表上 UPDATE post SET like_count = like_count + 1，热门帖子会变成行锁热点，拖慢同一行的其他更新。

## 要点

- 量级：日点赞几万、单帖峰值每秒几十次以内，关系表和内容表的计数列在同一事务里更新就够；单个对象每秒上百次以上才把计数拆出去。
- 关系表：post_like(post_id, user_id, created_at)，主键 (post_id, user_id)，另建 (user_id, created_at) 索引查“我赞过的”；INSERT 遇到唯一冲突视为已赞，幂等返回；取消直接删除。
- 计数：Redis 用 Hash，HINCRBY cnt:post:<帖子ID> like 1，同一个 Hash 里放 like、comment、fav；插入影响 1 行才加 1，删除影响 1 行才减 1。
- 合并写库：计数变化量在 Redis 或进程内累积，每 5–10 秒批量刷到 post_stat(post_id, like_count, …)，执行 UPDATE post_stat SET like_count = like_count + 增量；进程崩溃丢掉的增量由每日重算补回。
- 已赞状态：列表页每页 20 条，用一条 WHERE user_id = ? AND post_id IN (…) 批量查出，不逐条查；登录用户量大时在 Redis 里为每个用户保留最近 1000 条点赞的有序集合。
- 防刷：同一用户对同一对象每秒最多操作 1 次，客户端 300ms 防抖只提交最后状态；风控标记的账户点赞不计入展示数。
- 展示和校准：超过 1 万显示为“1.2 万”；每天按关系表 COUNT 重算热门对象和随机抽样对象的计数，修正 Redis 和 post_stat。
- 只要数、不要关系的阅读数用 INCR 加定时落库；按人去重的访客数用 HyperLogLog（PFADD、PFCOUNT，标准误差约 0.81%）。

## 提示词

在{项目}里实现{内容对象，如帖子、评价}的点赞与计数：先确认量级——日点赞数、单个对象峰值每秒点赞数、列表每页条数、计数能接受多久的延迟；单对象每秒几十次以内时，关系表和计数列同事务更新就够。再按以下设计：
1. 建点赞关系表，(对象 ID, user_id) 为主键，唯一冲突视为已赞，取消直接删除。
2. 插入或删除影响 1 行时才 HINCRBY 计数，变化量每 5–10 秒合并刷到统计表。
3. 列表页用 user_id 加 IN 一次查出已赞状态。
4. 同一用户对同一对象每秒最多 1 次，客户端 300ms 防抖。
5. 每天按关系表重算热门和抽样对象的计数并校准。
最后给出压测和对账方法：500 个用户对同一对象并发点赞、取消共 1 万次，断言关系表行数与最终计数一致；每天随机抽 1000 个对象比对计数与 COUNT(*)，偏差超过 1% 告警。
