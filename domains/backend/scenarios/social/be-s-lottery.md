## 是什么

用户消耗次数或积分参与抽奖，按配置的概率抽中奖品，奖品有总量和每日上限。要同时保证三件事：概率按配置执行、奖品不超发、每次抽奖和中奖记录可追溯。

## 适合

大转盘、九宫格、开盲盒、下单后抽红包、连续签到满 7 天抽奖。

## 不适合

先到先得的限量抢购看「秒杀」；奖品是平台积分以外的资金类权益时，规则先请法务确认。

## 注意

概率和库存是两件事：按概率抽中了某个奖，但它的库存已经发完，结果必须落到兜底奖或“谢谢参与”，不能超发；扣库存要原子。抽奖结果由服务端用安全随机数算出，前端转盘只负责转到指定的格子。

## 要点

- 量级：参与人数几千、奖品几十份，单库一个事务完成扣次数、抽取、扣奖品库存、写记录就够；几十万人同时抽再把次数和库存放进 Redis。
- 配置：lottery_prize(activity_id, prize_id, name, type 实物 / 券 / 积分 / 谢谢参与, weight, total, daily_limit, version)；权重用整数，总和 10000（万分之一精度），“谢谢参与”也是一个有权重的奖项；配置修改留版本，上线前要审批。
- 抽取：应用侧用安全随机数（Java SecureRandom、Node crypto.randomInt、Python secrets）生成 [0, 10000) 的整数，按累积权重区间找到奖项。
- 原子扣减：一条 Lua 脚本依次 DECR 用户剩余次数（小于 0 则加回并返回无次数）、DECR 奖品总库存和当日库存（任一小于 0 则加回并改为兜底奖）、返回结果；随机数作为参数传入脚本，不在脚本里生成。
- 记录和发奖：lottery_record(record_id, activity_id, user_id, prize_id, status 待发放 / 已发放 / 发放失败, request_id 唯一) 异步落库；券和积分调用对应服务时用 record_id 做幂等键（见「幂等键」），实物生成待发货单；发放失败按退避重试，最终失败转人工补发。
- 节奏：大奖按时段分配库存（如每小时最多 1 个），避免开场几分钟就被抽完；每人每日中奖上限，中过大奖的用户大奖权重降为 0。
- 防刷：参与资格（实名、注册天数、设备）在抽之前校验，每人每日次数上限，接口按用户限频；异常集中中奖的账号先冻结发放再人工复核。
- 公示：奖品、概率、数量和活动时间在活动页公示；有奖销售的最高奖金额等限制以现行法规为准。

## 提示词

在{项目}里实现{活动名}抽奖：先确认量级——参与人数、峰值每秒抽奖次数、奖品种类和数量、每人次数规则、有没有每日或每时段上限；参与人数几千时，单库一个事务完成扣次数、抽取、扣库存、写记录就够。再按以下设计：
1. 建奖品配置表，权重为整数且总和 10000，谢谢参与也是一个奖项，配置带版本。
2. 应用侧用安全随机数生成 [0, 10000)，按累积权重区间确定奖项。
3. 一条 Lua 脚本原子扣用户次数、奖品总库存和当日库存，库存不足改为兜底奖，随机数作为参数传入。
4. 抽奖记录 request_id 唯一，异步落库；发奖用 record_id 做幂等键，失败重试后转人工。
5. 大奖按时段分配库存，每人每日中奖设上限。
最后给出压测和对账方法：对抽取函数模拟 100 万次，各奖项命中率与配置偏差在 0.5% 以内；1000 并发抽到奖品耗尽，断言发放数不超过总量；活动结束核对 已发放 + 剩余 = 总量，次数扣减与抽奖记录数一致。
