## 是什么

生成 PDF 有四条路：用无头浏览器把 HTML 打印出来；用分页排版引擎按打印 CSS 排版；用 Typst、LaTeX 这类排版语言编译；用代码库直接画到页面上。按文档长相、谁来维护模板、运行环境和量级挑一条，而不是一上来就默认“HTML 转 PDF”。

## 适合

新项目第一次要导出 PDF；现有方案出现中文乱码、分页难控、并发撑不住或许可证有风险，准备换方案。

## 不适合

方案已经定了、只关心部署和并发，看「服务端批量生成」；纸张、边距、字体这些版式规则看「页面尺寸与边距」「字体嵌入与中文」。

## 注意

许可证先查。iText、PyMuPDF（MuPDF）、Ghostscript 是 AGPL 或商业授权，闭源的商业服务通过网络对外提供功能同样落在 AGPL 的义务范围里，要么买商业授权，要么换 Apache、MIT、BSD 许可的替代品。Poppler（pdftoppm、pdftotext）和 pdftk 是 GPL，作为独立命令行进程调用和链接进自己的程序义务不同，拿不准的交给法务。

## 要点

- 要和网页长得一样、前端已有页面或报表：「无头浏览器打印」（Puppeteer、Playwright 的 page.pdf），模板就是 HTML 加打印 CSS，前端能维护。
- 长文档要书籍级分页（页眉随章节变化、目录带页码、脚注、交叉引用）：「打印 CSS 与分页排版引擎」（WeasyPrint、Paged.js）或「Typst 排版」。
- 公式多、学术排版、已有 LaTeX 模板：「LaTeX 排版」（XeLaTeX + ctex）；其余场景 Typst 编译快、语法简单，优先于 LaTeX。
- 量大、版式固定的单据，或运行环境装不了浏览器：Typst（单个二进制）或「代码直接绘制」（ReportLab、PDFKit），单份几十毫秒，同一台机器的吞吐是无头浏览器的几倍到十几倍。
- 在设计好的 PDF 底版上套打（证书、票据、签字页）：pdf-lib 按坐标叠加文字；底版带表单域的走「填写表单」。
- React 团队、版式以卡片和列表为主、想在浏览器里直接生成下载：「组件式生成」（@react-pdf/renderer）。
- 单用户、几页、数据已在前端的可以放到浏览器端生成；涉及金额、签章、要留档的单据在服务端生成并存档。
- 定方案前拿同一份真实样本在两三个候选上各出一份：样本里要有 300 行以上的明细表、生僻字（如“𠮷”“䶮”“堃”）、超长英文单词和图片，比较版式、单份耗时、内存峰值和文件大小。

## 提示词

给 {产品} 选一个 PDF 生成方案。要生成的文档是 {文档类型}（如订单发票、月度经营报告、员工手册），每天约 {每日份数} 份、单份 {页数范围} 页，后端是 {后端语言与框架}，部署在 {部署环境}（如 Docker、Kubernetes、云函数）。
1. 先读现有代码：有没有在用的 PDF 库、前端有没有可复用的页面、服务器能不能装 Chromium 和中文字体。
2. 从这几条路线里选主方案：无头浏览器打印（Puppeteer / Playwright）、分页排版引擎（WeasyPrint / Paged.js）、Typst、LaTeX、代码绘制（pdf-lib / PDFKit / ReportLab）、组件式（@react-pdf/renderer）。写清选它和放弃其他路线的理由，以及中文字体、页眉页脚页码、表格跨页各怎么实现。
3. 列出依赖的许可证；用到 iText、PyMuPDF、Ghostscript 这类 AGPL 组件时单独标出，并给出 Apache / MIT / BSD 许可的替代。
4. 用一份真实样本验证：300 行以上的明细表、生僻字、超长英文单词、几张图片；报告单份耗时、内存峰值、文件大小，以及服务器缺字体、数据为空、单个字段超长时的表现。
5. 最后给出接入步骤和要改的文件，这一步先不大改现有代码。
