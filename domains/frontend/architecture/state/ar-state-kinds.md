## 是什么

先把状态分成五类：服务端数据、URL 状态、表单状态、客户端全局状态、组件局部状态，再按类别决定放在哪里；能从别的状态算出来的不单独存。

## 适合

全局 store 越写越大，数据在几处来回同步；同一份数据在 store、组件状态和 URL 里各存一份；接手一个状态到处飞的项目，先定规矩再动手。

## 不适合

每类的具体写法看「服务端状态缓存」「状态放进 URL」「表单状态与校验」「全局状态库」；步骤多、状态互斥的流程看「用状态机管流程」。

## 注意

能算出来的不存：订单总价、筛选后的列表、是否全选，都从源数据计算。多存一份就要写同步代码，迟早不一致。

## 要点

- 归属按顺序问：后端来的数据 → 服务端状态缓存；刷新或分享链接后要保留 → URL；用户正在填、还没提交 → 表单状态；不相邻的多个页面或组件都要用 → 全局 store；都不是 → 组件局部状态。
- 局部优先：状态放在用到它的组件的最近公共父组件；跨 2 层以内用 props，更深或者兄弟分支都要用时用 Context / provide-inject，再往上才进全局 store。
- 派生值直接计算：React 在渲染时算（计算重的用 useMemo），Vue 用 computed；用 useEffect / watch 把一个状态“同步”到另一个状态的写法，一律改成计算。
- 每个字段只有一个真实来源；需要临时编辑副本时明确命名为 draft，提交或取消时丢弃。
- 全局 store 只放客户端全局状态：当前用户摘要、主题、侧栏折叠、全局通知、未登录时的购物车；列表和详情数据归缓存层。
- Context / provide 只放变化不频繁的值（主题、当前门店、权限）；高频变化的值放进 React Context 会让所有消费者一起重渲染，改用 store 加 selector。
- 本地持久化只用于偏好和草稿：键名带应用名和版本（mall:v2:sidebar），读取失败或版本不符时回退默认值。

## 提示词

梳理 {产品} 前端的状态归属，行为保持不变：
1. 盘点：列出全局 store 的每个字段、每个 Context / provide、透传超过 3 层的 props，以及用 useEffect / watch 把一个状态同步到另一个状态的代码。
2. 给每项标类别（服务端数据 / URL / 表单 / 客户端全局 / 局部 / 可派生），写出现在在哪、应该在哪，做成迁移表，等我确认。
3. 按表迁移，每次只迁一类：可派生的改成计算；服务端数据交给请求缓存层；需要分享和刷新保留的筛选、页码、标签页移到 URL；只在一处使用的全局字段下放回组件。
4. 每迁完一类，核对刷新、前进后退、切换页面再回来、多个组件同时显示同一数据这几种情况，表现与原来一致。
5. 汇报删掉的 store 字段和同步代码、新增或改动的文件、还没决定去向的状态。
