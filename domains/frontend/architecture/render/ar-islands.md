## 是什么

服务端渲染出 HTML 后，浏览器要把事件和状态“接上”才能交互，这一步叫水合。孤岛架构只给页面上需要交互的几块（搜索框、加入购物车按钮、轮播）水合，其余部分保持纯 HTML，下载和执行的 JS 少得多。

## 适合

内容为主、交互零散的站点（官网、文档、博客、活动页）；SSR 页面首屏出得很快，但点了没反应；控制台出现 hydration mismatch 警告。

## 不适合

整页都在交互的后台和编辑器按单页应用做，看「渲染模式选型」；只是包太大看「代码分割与懒加载」。

## 注意

水合不匹配大多因为服务端和浏览器渲染出的结果不同：当前时间、随机数、时区和语言格式化、在渲染时读 window 或 localStorage、浏览器插件改了 DOM。要修根因，压掉警告只会让页面在某些用户那里错乱。

## 要点

- 默认不水合：组件先按静态 HTML 写，只有需要事件和浏览器状态的才标成交互组件（Astro 的 client:* 指令、React / Next.js 的 'use client' 边界、Nuxt 的 .client.vue 和懒水合）。
- 交互边界推到叶子：'use client' 加在按钮、表单这类小组件上；加在布局或页面上会把整棵子树都打进客户端包。
- 按时机选水合：首屏立即要用的用 load；可以等主线程空闲的用 idle；首屏以下的用 visible；只在某个断点出现的用 media。
- 服务端和浏览器的首次渲染必须一致：时间、随机数、本地化格式在服务端算好传下去；窗口宽度、localStorage 这类只有浏览器才有的值在挂载后再读，首帧给占位。
- 孤岛之间共享的状态（购物车数量、登录用户）放进轻量 store 或自定义事件，各孤岛各自订阅。
- 渐进增强：搜索、加入购物车这类关键操作在水合完成前用原生表单提交或链接也能完成。
- 用数据验收：对比改前改后的页面 JS 体积、总阻塞时间和 INP，写进 PR 描述。

## 提示词

请减少{产品}的{页面}的水合开销。先读页面结构，列出每个组件：是否需要事件或浏览器状态、在首屏内还是首屏下、当前是否被水合，并记录当前页面的 JS 体积。
按规则改：
1. 不需要交互的组件改成纯服务端输出，不进客户端包。
2. 交互边界推到最小的叶子组件，用{框架}的方式标记（如 client:* 指令或 'use client'）。
3. 水合时机：首屏要用的立即水合，其余等空闲或进入视口再水合。
4. 孤岛之间要共享的状态放进轻量 store，各自订阅。
5. 逐个修控制台里的水合不匹配：时间、随机数、本地化格式在服务端算好传下去，浏览器才有的值挂载后再读、首帧给占位。
6. 关键操作在水合前用原生表单或链接也能完成。
完成后汇报：改前改后的 JS 体积、仍在水合的组件及理由、改了哪些文件；验证：禁用 JS 时内容完整，弱网下首屏关键按钮可用，控制台没有水合警告。
