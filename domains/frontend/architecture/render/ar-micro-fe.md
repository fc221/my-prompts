## 是什么

把一个大前端按业务拆成多个能独立开发、独立部署的子应用，由主应用（基座）按路由加载。常见做法有 iframe、qiankun / wujie 这类运行时框架、Module Federation 和 Web Components。

## 适合

多个团队各管一块业务、发布节奏不同；老系统（jQuery、Vue 2、AngularJS）要渐进迁移，新旧页面并存；把多个独立后台聚合到同一个入口。

## 不适合

一个团队维护的单个应用，用「多包仓库」加「模块边界与依赖方向」就够；只想复用组件就发成 npm 包；页面里嵌一个第三方小部件，用 iframe 或 Web Component 即可。

## 注意

微前端解决的是组织和部署问题，不是性能问题。它会带来样式冲突、重复依赖、跨应用通信和整体联调的成本，只有“多团队独立发布”或“老系统渐进迁移”这类需求真实存在时才值得付出。

## 要点

- 按业务域拆：一个子应用对应一个完整业务（订单、会员、报表），有自己的路由前缀 /order/*、/member/*。
- 基座只做四件事：登录态、全局导航和外壳、子应用注册与路由分发、公共依赖的版本约定。业务代码全部在子应用里。
- 选方案看隔离需求：子应用是第三方或老系统、要强隔离 → iframe 或 wujie 这类基于 iframe 沙箱的方案；技术栈相同、要共享依赖和组件 → Module Federation；多技术栈混合、需要 JS 沙箱和样式隔离 → qiankun 这类运行时方案。
- 样式隔离：子应用的 CSS 加统一前缀或用 CSS Modules，必要时放进 Shadow DOM；子应用不写全局标签选择器，也不改 html、body 的样式。
- 通信只走约定的通道：URL、基座下发的只读上下文（用户、租户、权限）、带类型定义的事件；子应用之间不 import 对方代码、不读对方的 store。
- 公共运行时（React / Vue、组件库）由基座约定大版本并共享单例；版本对不上的子应用自带一份，并放在隔离容器里运行。
- 每个子应用能单独启动（带一个模拟基座）；在基座里加载失败时，只在该区域显示错误和重试，导航照常可用。
- 子应用独立部署：产物带版本号，基座从清单文件或配置中心读取入口地址，可以灰度、可以回滚到上一版。

## 提示词

请评估并落地{产品}的微前端拆分。先读现有代码、部署方式和团队分工，回答：有几个团队、分哪些业务域、发布节奏是否不同、有没有必须保留的老系统。如果既没有多团队独立发布，也没有老系统要迁移，直接建议改用多包仓库加模块边界，说明理由后停下。
确实需要拆时：
1. 按业务域列出子应用和各自的路由前缀。
2. 基座只负责登录态、导航外壳、子应用注册和路由分发。
3. 按隔离需求在 iframe 沙箱、Module Federation、运行时沙箱框架之间选一种，写明理由。
4. 定通信约定：URL、基座下发的只读上下文、带类型的事件；子应用之间互不 import。
5. 子应用样式加前缀或模块化，不写全局标签选择器。
6. 每个子应用能单独启动；加载失败时只在该区域显示错误。
完成后汇报拆分方案和改了哪些文件；验证：各子应用单独启动、在基座里来回切换路由、停掉某个子应用的服务时其他区域照常可用。
